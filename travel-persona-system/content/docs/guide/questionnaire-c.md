# Part C — 이번 여행 정보 (v2.0)

> **언제 묻는가**: **여행을 새로 계획할 때마다 매번**. 그래서 Part A(40문항)·Part B(46문항)와 정반대로, 최대한 짧고 빠르게 끝나야 한다.
> **무엇을 만드는가**: 이번 한 번의 여행에 한정된 정보(`user_trip_contexts` 레코드 1건) + Part A 성향을 이번 여행만 잠깐 조정하는 **축 오버라이드**.
> **문항 수**: 18문항 (그중 다수는 Part B 응답으로 기본값이 자동으로 채워져 있어 실제로 사용자가 손대야 하는 항목은 훨씬 적다).
> 다른 파트: [Part A — 성향 진단](/docs/questionnaire-a) · [Part B — 여행 취향 프로필](/docs/questionnaire-b) · [전체 개요](/docs/overview)

---

## 0. 설계 원칙 — "Part B는 기본값, Part C는 오버라이드"

Part B에서 이미 물어본 것(평소 식사 예산, 평소 동행자, 평소 숙소 필수시설 등)을 Part C에서 또 처음부터 물어보면 사용자는 피로해진다. 그래서 Part C의 각 문항은 가능한 한 **Part B 값으로 미리 채워진 상태**로 제시하고, 사용자는 "이번엔 다르면 바꾸기"만 하면 되도록 설계한다.

| 예시 | Part B (기본값) | Part C 화면에 보이는 것 |
|---|---|---|
| 한 끼 식사 예산 | `default_meal_budget_tier` = "2~4만원" | 미리 "2~4만원"이 선택된 상태로 표시, 필요하면 이번만 변경 |
| 동행자 | `default_companion_type` = "연인" | 미리 "연인"이 체크된 상태, 이번엔 "친구"로 바꿀 수도 있음 |
| 숙소 필수시설 | `lodging_amenity_requirements[]` | 그대로 상속, 이번 여행만 "온천" 하나 추가하는 식으로 편집 |

이 원칙 덕분에 Part C는 "18문항"이라고 되어 있지만 실제 사용자가 매번 새로 입력해야 하는 항목은 보통 **동행자·기간·목적지·예산 정도(5~6개)** 뿐이다.

## C-5. 축 오버라이드 — "이번 여행만큼은" (4문항)

Part A에서 나온 성향은 "평소의 나"다. 하지만 사람은 늘 평소 모습대로 여행하지 않는다 — 평소엔 계획적인 사람도 번아웃이 와서 이번엔 완전히 즉흥적으로 쉬고 싶을 수 있고, 평소 조용한 걸 좋아하는 사람도 오랜만의 친구 모임에서는 왁자지껄하게 놀고 싶을 수 있다. 그래서 Part C 마지막에 축마다 **"이번만 다르게" 슬라이더**를 둔다.

| # | 문항 | 필수 | 유형 | 기본 위치 | 저장 필드 |
|---|---|---|---|---|---|
| C5-1 | 이번 여행, 사람들과 어울리고 싶은 정도는? | | 슬라이더(1~5) | 평소 `social_score` 위치에 기본값 표시 | `social_score_override` |
| C5-2 | 이번 여행, 새로운 것에 도전하고 싶은 정도는? | | 슬라이더(1~5) | 평소 `adventure_score` 위치 | `adventure_score_override` |
| C5-3 | 이번 여행, 특별한 경험에 쓰고 싶은 정도는? | | 슬라이더(1~5) | 평소 `experience_score` 위치 | `experience_score_override` |
| C5-4 | 이번 여행, 계획대로 움직이고 싶은 정도는? | | 슬라이더(1~5) | 평소 `flow_score` 위치 | `flow_score_override` |

- UI 문구 예시(C5-1): "평소보다 조용히 쉬고 싶어요 ↔ 평소보다 사람들과 어울리고 싶어요" 양 끝단 라벨의 슬라이더, 가운데 기본 위치는 사용자의 `social_score`.
- **슬라이더를 건드리지 않으면 저장값은 NULL** — 즉 "이번엔 평소랑 똑같이"라는 뜻이며, 알고리즘은 Part A의 원래 점수를 그대로 쓴다. 슬라이더를 움직인 경우에만 그 값이 이번 여행에 한해 원래 점수를 대체한다.
- 4문항 모두 **선택**이다. 대부분의 사용자는 건드리지 않고 지나갈 것이므로 "더 보기"를 눌러야 나오는 형태로 접어두는 걸 권장한다.

### 오버라이드 적용 공식

```
effective_social_score      = COALESCE(trip.social_score_override,      persona.social_score)
effective_adventure_score   = COALESCE(trip.adventure_score_override,   persona.adventure_score)
effective_experience_score  = COALESCE(trip.experience_score_override,  persona.experience_score)
effective_flow_score        = COALESCE(trip.flow_score_override,        persona.flow_score)
```

이 `effective_*_score` 값이 [restaurant-recommendation-design.md](/docs/restaurant-recommendation-design) 4.4절/6.4절의 `weight = base + k × (axis_score - 0.5)` 공식에 들어간다. 즉 **오버라이드는 페르소나 자체를 바꾸지 않고, 이번 여행의 추천 계산에만 영향을 준다.** 관련 DB 컬럼(`user_trip_contexts.*_override`)은 같은 문서 3.4절에 추가했다.

## 2. 구현 메모

- Part C는 매번 반복되므로 **평균 완료 시간 60초 이내**를 목표로 한다. 실제로 사용자가 타이핑/선택해야 하는 항목은 필수 5개 + 상황별 조건부 항목 정도이고, 나머지는 Part B 기본값을 그대로 쓰거나 건너뛸 수 있다.
- 직전 여행의 Part C 응답을 "지난번과 동일하게" 버튼으로 한 번에 복사할 수 있게 하면 반복 사용자의 마찰을 더 줄일 수 있다.
- `user_trip_contexts`는 여행마다 새 레코드를 만든다 — Part A/B와 달리 UPDATE가 아니라 INSERT다.
- C1-3, C4-2처럼 "조건부" 문항은 Part B 값에 따라 아예 화면에 노출되지 않을 수 있다 — 불필요한 질문을 원천적으로 줄이는 장치다.
