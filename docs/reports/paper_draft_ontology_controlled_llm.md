# 온톨로지 기반 통제형 LLM을 활용한 노코드 자동화 프레임워크

> **작성 기준**: 실제 서비스 코드베이스(`server/*.py`, `chatbot/*`, `docs/technical/*.md`) 대조 검증 + 온톨로지 자동 일관성 검증 스크립트 실행 완료
> **비교 baseline**: GPT-4o (raw, 프레임워크 미적용), 교차검증 baseline: Gemini — 선정 근거는 §2.4 참고
> **본 연구는 독립적인 설계·평가 연구로서, 특정 선행 연구를 확장하거나 그 한계를 비판하는 것을 목적으로 하지 않는다.** 이하 본문에서 인용되는 문헌은 RAG·통계 검정·LLM 평가 등에 사용된 개별 기법의 출처를 명시하기 위한 기술적 참조일 뿐, 본 연구의 문제의식이나 설계가 특정 선행 연구로부터 도출되었음을 의미하지 않는다.

## 요약

최근 노코드/로우코드 자동화 플랫폼의 확산에 따라, 비전문가도 복잡한 업무 자동화를 직접 설계할 수 있도록 지원하는 지능형 학습·생성 보조 시스템에 대한 수요가 증가하고 있다. 실제로 자동화 워크플로우 구축을 시도하는 대다수 사용자는 전용 도구 없이 ChatGPT(GPT-4o)와 같은 범용 상용 LLM에 직접 질의하는 경우가 많으나, 범용 LLM은 플랫폼이 보유한 수백 종의 노드와 수천 개의 파라미터 스펙을 정확히 기억하지 못해 존재하지 않는 파라미터명이나 폐기된 문법을 생성하는 환각(Hallucination) 문제를 일으킨다.

이러한 문제는 감정 분석이나 스팸 판정처럼 출력이 소수의 고정된 라벨로 닫혀 있는 폐쇄형 출력 도메인(Closed Output Domain)과, 노코드 워크플로우 설계·JSON 토폴로지 생성·수식 작성처럼 출력 후보를 사전에 유한한 목록으로 열거하기 어려운 고차원 조합적 출력 공간을 갖는 개방형 출력 도메인(Open Output Domain)을 구분했을 때 그 구조적 원인이 더 명확해진다. 본 연구는 후자를 개방형 출력 도메인으로 조작적으로 정의하고, 이 구분을 학계에 확립된 공식 분류 체계가 아닌 본 연구의 작업상 정의로 사용한다. 폐쇄형 도메인에서는 검색 증강 생성이나 온톨로지 기반 프롬프트 그라운딩 같은 입력 단계 통제만으로도 환각을 상당 부분 억제할 수 있는 반면, 개방형 도메인에서는 입력 단계 통제만으로 생성 과정의 세부 구조·문법 오류를 완전히 방지하기 어려울 수 있다는 것이 본 연구의 문제의식이다 — 이에 따라 생성 과정 자체를 가로채고 실행 결과까지 검증하는 전주기적 개입이 필요하다고 본다. 본 연구는 n8n 워크플로우 자동화 플랫폼을 사례로, 이러한 개방형 출력 도메인에서 LLM의 환각을 통제하고 실행 가능한 산출물을 검증하기 위한 전주기 하네스 엔지니어링(Comprehensive Harness Engineering) 프레임워크를 제안하고, 이를 **동일한 상용 LLM 엔진 기반의 프레임워크 미적용(raw) 상태**와 정량적으로 비교하여 프레임워크 자체의 효과를 실증한다. 하네스 엔지니어링은 모델 가중치를 전혀 수정하지 않고 H = (H_pre, H_post, H_exec) — 생성 전 사전 생성 하네스(Pre-generation Harness), 생성 후 사후 처리 하네스(Post-generation Harness), 실행 시점 런타임 실행 하네스(Execution Test Harness) — 로 LLM을 감싸는 구조로 본 연구에서 정의한다(상세 정의는 §3.1).

사전 생성 하네스는 노드 분류·관계 그래프·속성 제약·검증된 패턴·학습 선행 그래프로 구성된 5계층 온톨로지(723개 노드, 787개 관계 엣지, 30개 속성 제약 규칙)를 통해 LLM 입력 단계에서 의미 문맥을 주입하며, 자동화된 일관성 검증 결과 관계 그래프의 자기 참조(self-loop) 0건, 제약 규칙 간 모순(REQUIRES-FORBIDDEN 충돌 등) 0건, 패턴 라이브러리의 노드 참조 무결성 위반 0건을 확인하였다. 명백한 신호(에러 로그 첨부, 플랫폼 고유 JSON 첨부, 대화 꼬리물기)에 대해서만 규칙 기반 고속 경로를 적용하고 나머지 자연어 질의는 LLM이 판단하되 LLM의 회피 응답을 키워드 신호로 구제하는 하이브리드 의도 분류기로 질의를 6가지 처리 경로로 라우팅한다. 이 LLM 분류 호출에는 목적 서술형 질의에서 텍스트 매칭만으로는 놓치는 암묵적 필요 노드를 보완하기 위해 HyDE 방식의 사전 맥락 확장을 편승시켜 추가 지연 없이 온톨로지 탐지 재현율을 높였다. 처리 경로별로는 규칙 기반 출력 통제(Output Restriction)로 생성 형식을 강제한다. 사후 처리 하네스는 Levenshtein 편집 거리 기반 규칙 기반 교정기가 잘못된 파라미터명을 자동으로 교정하고, 이와 별개로 구조·속성 제약·관계 패턴·표현식 문법을 진단하는 규칙 기반 검증기가 위반 사항을 사용자에게 투명하게 노출하는 두 계층으로 구성된다.

평가 방법론은 다음 네 가지 원칙에 따라 설계하였다. 첫째, 파라미터 정합률(PCR)·실행 가능률(EFR)·구조 정합도(SA)는 사람의 주관적 판단이 아닌 n8n 공식 스펙 대조·런타임 실행 하네스·JSON 스키마 검증기를 통해 **결정론적으로 자동 채점**하고, 판별이 불가능한 "근거 없는 능력 창작형 환각"만 시스템이 실제로 참조한 근거 문서와 응답을 대조하는 근거 대조 기반 인간 판정으로 분리한다. 둘째, 검정력 분석(power analysis)에 기반해 최소 표본 크기를 산정하고 경계·적대적 사례를 포함한 총 330문항 벤치마크를 구성한다. 셋째, Raw LLM / H_pre(사전 생성 하네스)만 적용 / H_pre+H_post(제안 프레임워크 전체) 적용의 3단 비교를 GPT-4o와 Gemini 두 모델에 대해 반복함으로써, H_pre와 H_post 각각의 기여를 분리하는 동시에 개선 효과가 특정 모델에 국한되지 않음을 교차 검증한다. 넷째, 질의를 무작위 효과로 포함하는 혼합효과모형과 McNemar 검정·Wilcoxon 부호순위 검정을 병행하고 다중비교 보정(Holm-Bonferroni)과 효과크기·95% 신뢰구간을 함께 보고하는 통계 분석 계획을 사전에 명시한다. 이러한 설계는 런타임 실행 하네스가 생성된 워크플로우 코드를 실제 n8n 인스턴스에 자동 주입해 실행 가능성까지 검증한다는 점과 결합되어, 재현 가능하고 통계적으로 방어 가능한 평가 체계를 구성한다.

이 평가 체계를 WORKFLOW_BUILD 인텐트에 대해 GPT-4o 단일 모델·N=330 규모로 실제로 실행한 결과(§4.10), 파라미터 정합률(PCR)은 1차 분석(GEE)과 강건성 검정(Wilcoxon·McNemar)이 모두 p<0.0001로 일치하는 유의한 개선을 보였고(완전정합률 24.0%→39.7%, 파라미터 단위 승산비 1.56), 규칙 기반 교정기의 편집 거리 임계값 설계를 뒷받침하는 강한 음의 상관(RCR-파라미터명 길이, ρ≈-0.58~-0.69)도 표본 규모에 걸쳐 안정적으로 재현되었다. 반면 사후 처리 하네스가 실행 가능률(EFR)을 추가로 개선하는지는 지지되지 않았으며(이는 사전 생성 하네스 단계에서 EFR이 이미 88.9%→98.4%로 크게 개선되어 있었기 때문으로 해석된다), 가중 이슈 점수(WIS)는 예측과 반대 방향으로 유의하게 나타나 규칙 기반 검증기의 제한된 점검 범위가 만드는 측정 편향의 가능성을 드러냈다. 본 실행은 GPT-4o 단일 모델·단일 인텐트·전량 합성 벤치마크로 한정되므로, 교차모델 일반화·환각률 감소·재현성 향상에 대한 주장으로는 확장하지 않는다.

## 1. 서론

최근 비개발자도 소프트웨어 개발 지식 없이 업무 자동화 워크플로우를 구성할 수 있는 노코드/로우코드 자동화 플랫폼의 사용이 급격히 증가하고 있다. 그러나 이러한 플랫폼은 수백 종의 노드와 노드별 수십 개의 파라미터, 그리고 독자적인 표현식 문법을 가지므로, 신규 사용자가 스스로 학습하여 워크플로우를 설계하기까지의 진입 장벽이 높다는 한계가 존재한다. 본 연구가 대상으로 하는 n8n 플랫폼은 실제 운영 인스턴스의 노드 카탈로그를 전수조사한 결과 706개의 노드(`n8n-nodes-base.*`)를 지원하는 것으로 확인되며, 자체 구축한 지식 코퍼스(14,543개 청크) 내에서도 빈도 3회 이상 기준 453종의 고유 노드가 확인될 만큼 도메인 지식의 폭이 넓다.

LLM은 자연어 질의를 이해하고 코드를 생성하는 능력 덕분에 이러한 자동화 학습·생성 보조 역할에 활용될 수 있다. 그러나 일반적인 LLM 사용에는 다음과 같은 한계가 있다. 첫째, 플랫폼이 보유한 방대한 파라미터 스펙을 학습 데이터만으로 정확히 기억하지 못해, 존재하지 않는 파라미터명(`retryOnFai`)이나 이미 폐기된 문법(`$item()`)을 자신감 있게 생성하는 사실 환각(Factual Hallucination) 문제가 발생한다. 둘째, 생성된 답변이 어떤 근거에서 도출되었는지 제시하지 못해 학습자가 정보를 검증할 수 없는 출처 불명확성(Source Opacity) 문제가 있다. 셋째, 사용자의 학습 수준이나 이전 대화 맥락을 지속적으로 추적하지 못해 매 턴마다 일관성이 결여된 응답을 생성하는 맥락 비일관성(Context Inconsistency) 문제가 있다.

본 연구는 이 세 가지 결함에 대응하기 위해, 온톨로지 기반 의미 문맥과 규칙 기반 판단을 결합하여 LLM의 역할을 "독립적 판단자"에서 "주어진 근거의 설명자"로 제한하는 통제형 생성(Controlled Generation) 프레임워크를 제안한다. 다만 이러한 통제형 생성 접근이 충분한지는 출력 공간의 성격에 따라 달라질 수 있다는 것이 본 연구의 문제의식이다. 감정 분석·스팸 판정·질병 분류처럼 출력이 소수의 고정된 라벨로 닫혀 있는 **폐쇄형 출력 도메인(Closed Output Domain)**에서는 검색 증강이나 온톨로지 기반 프롬프트 그라운딩 같은 입력 단계 통제만으로도 환각을 상당 부분 억제할 수 있다. 반면 본 연구는 n8n 노코드 워크플로우 설계, JSON 토폴로지 생성, 수식 작성처럼 노드·파라미터·문법의 조합을 사전에 유한한 목록으로 열거하기 어려운 출력 공간을, 이러한 폐쇄형 도메인과 대비되는 **개방형 출력 도메인(Open Output Domain)**으로 조작적으로 정의한다. 이 용어는 학계에 확립된 공식 분류 체계를 지칭하는 것이 아니라, 이하 서술의 편의를 위해 본 연구가 도입하는 작업상의 구분임을 밝혀둔다.

| 구분 | 폐쇄형 출력 도메인 (Closed Output Domain) | 개방형 출력 도메인 (Open Output Domain, 본 연구의 조작적 정의) |
|---|---|---|
| 대상 문제 | 감정 분석, 질병/스팸 분류, 단문 판정 | n8n 노코드 워크플로우 설계, JSON 토폴로지, 수식 작성 |
| 출력 특성 | 선택지(라벨)의 수가 소수로 고정됨 | 출력 후보를 사전에 유한한 목록으로 열거하기 어려운 고차원 조합적 출력 공간 |
| 환각 억제 방식 | 프롬프트 제약 및 검색 증강(입력 단계 통제)만으로 비교적 충분 | 입력 단계 통제만으로는 세부 오타·문법 누락을 완전히 방지하기 어려울 수 있음(본 연구의 가설) |
| 본 연구의 대응 | — | 입력 단계 통제에 더해 생성 후 가로채기(사후 교정·검증)와 실행 시점 검증이 필요하다고 본다 |

즉 본 연구는 개방형 출력 도메인에서는 "입력 단계에서 문맥을 주입해 출력을 제한하는 것"만으로는 생성 과정에서 발생하는 세부 오류를 완전히 방지하기 어려울 수 있다고 본다. 제한된 형식 내에서도 발생할 수 있는 세부적인 표기 오류(파라미터 오타, 폐기된 문법 사용 등)를 생성 이후 단계에서 능동적으로 탐지·교정하고, 나아가 산출물이 실제로 실행 가능한지까지 검증하는 메커니즘이 추가로 필요할 수 있다는 것이 본 연구의 핵심 문제의식이자 가설이다.

이에 본 연구는 모델의 가중치를 전혀 수정하지 않고, 모델의 앞단(입력 통제)·뒷단(사후 가로채기)·외부(런타임 검증)를 결정론적 규칙과 지식 구조로 감싸는 3단계 **하네스 엔지니어링(Harness Engineering)** 체계로 온톨로지 기반 문맥 그라운딩과 규칙 기반 통제 생성을 확장한 프레임워크를 정식화한다(하네스 엔지니어링이라는 관점이 갖는 더 넓은 공학적 맥락과 관련 산업 사례는 §2.6에서 별도로 논의한다). 아울러 본 연구는 실제 운영 코드베이스를 기준으로 설계 의도와 실제 구현 범위를 구분하여 보고함으로써, 설계는 되었으나 아직 시스템에 연결되지 않은 구성요소를 명시적으로 밝힌다.

한편 이러한 아키텍처 설계가 실제로 효과가 있는지는 내부 구성요소 간 비교만으로는 충분히 입증되지 않는다. n8n 자동화에 대해 궁금한 실제 사용자 다수는 전용 온톨로지·RAG 시스템이 아니라 ChatGPT(GPT-4o)와 같은 범용 상용 LLM에 직접 질문하는 것이 현재의 일반적인 사용 양상이다. 따라서 본 연구는 제안 프레임워크를 내부 구성요소 간 비교에 그치지 않고, 실제 사용자가 대안으로 선택할 법한 범용 상용 LLM의 raw 사용 상태와 정량적으로 비교함으로써, 프레임워크가 실제 대안 대비 갖는 효과를 실증적으로 검증한다. 나아가 본 연구는 이러한 비교가 특정 모델·소규모 표본·단일 평가자의 주관적 판단에 좌우되지 않도록, 결정론적 자동 채점과 검정력 분석 기반 표본 설계, 다중 모델 교차검증, 통계적 유의성 검정을 평가 방법론의 필수 요소로 스스로 채택한다.

한 줄로 요약하면, 본 연구는 **출력 후보를 사전에 열거하기 어려운 개방형 출력 도메인에서 LLM의 환각을 통제하고 실행 가능한 산출물을 검증하기 위한 전주기 하네스 엔지니어링 연구**로 정의할 수 있다. 다만 본 연구의 기여는 RAG·온톨로지·규칙 기반 검증·실행 테스트라는 개별 기술 자체의 신규성에 있지 않으며, 이러한 조합적 출력 공간에서 이들을 생성 전·생성 후·실행 시점의 전주기 통제 체계로 구조화하고 그 효과를 실증적으로 분리·검증하는 데 있다(신규성에 대한 상세 논의는 §2.5). 본 연구의 주요 기여는 다음과 같다.

**① 개방형 출력 도메인 문제 정의**: 단순 분류·판정 문제가 아닌 복잡한 워크플로우·코드 생성이라는, 출력 후보를 사전에 열거하기 어려운 개방형 출력 도메인에 특화된 환각 통제 방법론으로 문제 정의 자체를 확장하였다(§1, §2.5).

**② 3단계 하네스 프레임워크 H = (H_pre, H_post, H_exec)**: 모델 가중치를 수정하지 않고 생성 전·생성 후·실행 시점을 감싸는 통제 구조를 정식화하였다(§3.1). H_pre(사전 생성 하네스)와 H_post(사후 처리 하네스)는 응답 생성 자체에 관여하는 **생성 통제(Generation Control)** 계층이며, H_exec(런타임 실행 하네스)는 생성에는 관여하지 않고 이미 생성된 산출물의 실행 가능 여부만을 사후적으로 검증하는 **런타임 검증(Runtime Verification)** 계층이다 — 본 연구는 이 두 역할을 명확히 구분하여 설계하였다.

**③ 하네스 각 단계의 구체적 구현**:
- *H_pre*: 노드 분류(NodeTaxonomy)·관계 그래프(RelationGraph)·속성 제약(PropertyConstraints)·패턴 라이브러리(WorkflowPatterns)·학습 선행 그래프(LearningGraph)로 구성된 5계층 온톨로지를 설계하고 자동화된 스크립트로 내적 일관성(자기 참조·제약 모순·패턴 참조 무결성)을 검증하였다. 또한 순수 규칙 기반 의도 분류가 경계 사례(예: "Webhook 노드 설명해줘" 대 "이 워크플로우 어떻게 동작해?")에서 오분류를 반복한 설계 실패 경험을 바탕으로, 명백한 신호 3종은 규칙으로 즉시 처리하고 나머지는 few-shot LLM 분류에 맡기되 LLM의 회피 응답을 키워드 신호로 구제하는 **하이브리드 의도 라우터**를 구현하였다. 나아가 온톨로지의 노드 탐지가 텍스트 표면 언급에만 의존해 목적 서술형 질의의 암묵적 필요 노드를 놓치는 한계를 발견하고, HyDE[14]에서 착안하여 의도 분류와 동일한 LLM 호출에 편승하는 **사전 맥락 확장**을 추가함으로써 추가 지연 없이 탐지 재현율을 보완하였다(§3.2).
- *H_post*: 생성 결과를 그대로 신뢰하지 않고, Levenshtein 편집 거리 기반의 어휘 수준 사후 교정기와 워크플로우 구조·속성 제약·관계 패턴·표현식 문법을 진단하는 의미 수준 사후 검증기를 분리하여 도입함으로써, "교정 가능한 오류는 자동으로 고치고, 교정 불가능한 구조적 위반은 사용자에게 투명하게 알린다"는 역할 분리 원칙을 구현하였다.
- *H_exec*: 생성된 워크플로우 코드를 실제 n8n 인스턴스에 자동 주입하여 실행 실패 여부를 탐지할 수 있는 런타임 실행 하네스를 구축함으로써, 평가 대상을 자연어 설명의 정합성을 넘어 실행 가능한 산출물의 동작 여부까지 확장하였다.

**④ 결정론적 채점·단계별 비교·교차모델·통계적 실증을 결합한 평가 방법론**: PCR·EFR·SA를 사람의 주관적 판단이 아닌 결정론적 스크립트로 채점하고, 판별 불가능한 환각 유형만 근거 대조 기반 라벨링(reference-grounded labeling)으로 분리하여 도메인 지식이 없는 평가자도 라벨링을 수행할 수 있게 하였다. Raw LLM / H_pre만 적용 / H_pre+H_post 전체 적용의 단계별 비교를 GPT-4o·Gemini 교차모델에 대해 반복하고, 검정력 분석에 기반한 표본 크기 산정과 혼합효과모형·McNemar/Wilcoxon 검정·다중비교 보정·효과크기·신뢰구간 보고를 포함하는 통계 분석 계획을 사전에 설계함으로써, 재현 가능하고 통계적으로 방어 가능한 실증 방법론을 제시하였다(§4).

## 2. 배경 및 핵심 개념

본 장은 본 연구의 설계에 사용된 개별 기법(검색 증강 생성, 통계 검정 등)의 개념과 출처를 밝히기 위한 배경 설명이며, 본 연구를 특정 선행 연구의 연장선으로 위치시키기 위한 것이 아니다.

### 2.1 검색 증강 생성(RAG)과 환각

검색 증강 생성(Retrieval-Augmented Generation, RAG)은 외부 지식을 검색하여 LLM의 생성 입력으로 함께 제공함으로써 응답의 사실 일관성을 높이는 기법이다[1]. 환각(Hallucination)은 생성형 언어 모델이 입력과 무관하거나 사실과 다른 내용을 생성하는 현상을 가리킨다[2]. 본 연구는 단일 벡터 검색의 재현율(recall) 한계를 보완하기 위해 키워드 기반 희소 검색(BM25)[3]과 의미 기반 밀집 검색(BGE-M3 임베딩[5], 1024차원, ChromaDB 코사인 유사도)을 병렬 수행한 뒤 Reciprocal Rank Fusion(RRF, k=60)[4]으로 결합하는 하이브리드 검색 구조를 채택하였다.

### 2.2 온톨로지 기반 문맥 구조화

온톨로지는 특정 도메인의 개념과 그 관계를 구조적으로 명세하여 LLM 입력에 의미 문맥을 제공하는 지식 표현 방식이다. 단순 분류(개체가 어떤 범주에 속하는지)만 정의하는 온톨로지는 개체 간 상호작용 지식(예: "이 노드를 쓰면 저 노드도 함께 고려해야 한다")을 표현하지 못한다는 한계가 있다. 본 연구는 이러한 한계를 극복하기 위해, 노드 간 동시 사용 관계(COMMONLY_USED_WITH), 선행 요구 관계(PREREQUISITE_FOR), 상호 배제 관계(ANTI_PATTERN_WITH) 등 7종의 관계 유형과 가중치를 가진 관계 그래프(787개 엣지), 그리고 속성 간 제약 규칙(REQUIRES/CONFLICTS/CONDITIONAL/RECOMMENDED/FORBIDDEN, 총 30개)까지 포함하는 5계층 구조로 온톨로지를 독자적으로 설계하였다(상세 구조는 §3.3).

### 2.3 출력 통제와 통제형 디코딩

LLM 출력의 형식을 엄격히 지정하여 기계 파싱이 가능한 구조화 데이터로 취급하는 접근은, 디코딩 단계에서 이산적 편향(discrete biasing)을 가해 출력 구조를 직접 제약하는 통제형 디코딩 연구[8]와 마찬가지로 LLM을 자유 형식 텍스트 생성기가 아닌 구조화 데이터 생성기로 다룬다는 공통점을 가진다. 본 연구는 프롬프트 수준에서 의도별 출력 스키마를 강제하는 규칙 기반 출력 통제(Output Restriction)를 채택하였다(§3.5).

### 2.4 비교 baseline 선정 근거 — 범용 상용 LLM(GPT-4o) vs 실제 n8n 전문 AI 제품

본 연구는 내부 구성요소 간 비교(ablation)에 머무르지 않고, 실제 대안이 될 수 있는 외부 시스템과의 정량적 비교를 실험의 중심에 둔다. 비교 baseline으로는 (a) 시중에 존재하는 n8n 전문 AI 제품, (b) 범용 상용 LLM(GPT-4o, Gemini 등) 단독 사용 두 가지 후보를 검토하였고, 본 연구는 (b)를 최종 baseline으로 선정하되 GPT-4o를 주 baseline, Gemini를 교차검증용 2차 baseline으로 사용한다. 근거는 다음과 같다.

첫째, **엔진 고정을 통한 인과 분리(Engine-controlled comparison)**. 시중의 n8n 전문 AI 제품과 비교할 경우, 그 제품이 내부적으로 어떤 LLM을 사용하는지 알 수 없거나 통제할 수 없으므로, 성능 차이가 "프레임워크 설계의 차이" 때문인지 "기반 모델 자체의 성능 차이" 때문인지 분리할 수 없다. 반면 본 연구의 제안 프레임워크는 OpenAI BYOK(Bring Your Own Key) 경로로 GPT-4o를 엔진으로 직접 호출할 수 있도록 이미 구현되어 있으므로(`chatbot/lib/ai/providers.ts`), **동일한 LLM을 raw 상태와 프레임워크 적용 상태 양쪽의 공통 엔진으로 고정**할 수 있다. 독립변수(프레임워크 유무)만 조작하고 잠재적 교란변수(기반 모델의 성능)를 상수로 고정하는 것은 인과 추론의 기본 원칙이며, 본 연구는 이 원칙을 실험 설계에 직접 반영한다.

둘째, **재현성과 실험 통제 가능성**. 시중 n8n 전문 AI 제품은 (i) 특정 단일 제품이 시장 지배적 위치를 갖고 있지 않아 비교 대상 선정 자체에 자의성이 개입하고, (ii) 버전이 예고 없이 변경되어 동일 조건 재현이 어려우며, (iii) 상용 서비스의 API 접근성·요금제·이용약관상 벤치마킹 목적의 반복 호출이 제한될 수 있다. 반면 GPT-4o·Gemini는 API 스펙과 버전이 명시적으로 고정되어 있어 동일한 질의 집합에 대한 반복 실험과 결과 재현이 용이하다.

셋째, **실제 사용자 행동과의 외적 타당성(External Validity)**. n8n 자동화에 대해 궁금한 실제 사용자 다수는 전용 n8n AI 플러그인을 별도로 탐색하기보다 이미 사용 중인 ChatGPT(GPT-4o)에 직접 질문하는 것이 현재 가장 일반적인 행동 양상이다. 따라서 GPT-4o의 raw 사용 상태는 "본 시스템이 없었다면 사용자가 실제로 택했을 대안"을 가장 잘 근사하는 반사실적(counterfactual) 비교 대상이라 할 수 있다.

넷째, **모델 특이성 배제(Model-specificity control)**. GPT-4o 단일 모델만으로 개선 효과를 보고할 경우, 그 효과가 프레임워크 설계의 일반적 효용인지 GPT-4o라는 특정 모델의 개별 특성(예: 특정 파라미터명에 대한 학습 데이터 편향)과의 우연한 상호작용인지 구분할 수 없다. 이에 본 연구는 Gemini를 2차 baseline이자 교차검증 대상으로 채택하여, §4에서 서술할 혼합효과모형의 Tier×Model 상호작용항을 통해 개선 효과의 모델 일반화 가능성을 통계적으로 검증한다.

실제 n8n 전문 AI 제품이 향후 시장 지배적 위치를 갖게 될 경우의 3자 비교 확장은 §5.3의 향후 연구로 남겨둔다.

### 2.5 신규성에 대한 입장

§2.1~§2.3에서 정리한 바와 같이, 본 연구가 사용하는 개별 구성 요소 — 검색 증강 생성, 온톨로지 기반 문맥 주입, 규칙 기반 출력 통제, 편집 거리 기반 문자열 교정, 외부 시스템을 통한 실행 검증 — 은 각각 독립적으로는 이미 알려진 기법이다. 따라서 **본 연구의 기여는 이러한 개별 기술 자체의 신규성에 있지 않다.** 본 연구가 주장하는 기여는 다음과 같다: 출력 후보를 사전에 열거하기 어려운 조합적 출력 공간(§1의 개방형 출력 도메인)에서, 이러한 개별 기술들을 생성 전·생성 후·실행 시점이라는 전주기에 걸친 하나의 통제 체계 H = (H_pre, H_post, H_exec)로 구조화하고(§3.1), 각 단계가 실제로 기여하는 효과를 단계별 비교와 통계적 검정을 통해 분리·검증하는 방법론을 제시하는 데 있다(§4). 즉 "무엇을 조합했는가"가 아니라 "어떤 원칙으로 조합을 구조화했고, 그 구조화가 실제로 효과가 있음을 어떻게 실증했는가"가 본 연구의 주장이 위치하는 지점이다.

### 2.6 Harness Engineering과 모델 외부 통제

2026년 초 OpenAI는 코드 생성 에이전트 Codex를 이용해 사람이 직접 작성한 코드 없이 약 100만 줄 규모의 프로덕션 소프트웨어를 구축한 사례를 공개하며, 이 과정에서 얻은 공학적 교훈을 "하네스 엔지니어링(Harness Engineering)"이라는 이름으로 정리하였다[15]. 이 사례의 핵심 원칙은 "인간은 방향을 정하고 에이전트가 실행한다(Humans steer. Agents execute.)"는 문장으로 요약되며, 거대한 단일 지침 문서 대신 약 100줄 내외의 짧은 진입점 문서가 더 깊은 지식 체계로 안내하는 점진적 노출(progressive disclosure) 구조, 그리고 구조화된 로깅·네이밍 컨벤션·계층 간 의존성 방향과 같은 아키텍처 불변 조건을 커스텀 린터와 구조 테스트로 기계적으로 강제하는 방식을 보고하였다.

본 연구가 §3.1에서 정식화하는 H = (H_pre, H_post, H_exec) 역시, 모델 가중치를 변경하지 않고 모델 외부의 구조화된 지식과 결정론적 통제 계층을 통해 생성 신뢰성을 확보한다는 관점을 공유한다. H_pre가 온톨로지 탐지·사전 맥락 확장·하이브리드 검색을 통해 필요한 문맥만을 선택적으로 노출하는 방식은 앞서 언급한 점진적 노출의 설계 관점과, H_post·H_exec가 자연어 지시만으로 정확성을 기대하지 않고 결정론적 규칙과 외부 실행 환경으로 결과를 강제 검증하는 방식은 커스텀 린터·구조 테스트를 통한 기계적 강제의 설계 관점과 맥이 닿아 있다.

다만 두 사례가 다루는 문제는 본질적으로 다르다. OpenAI의 사례는 에이전트가 저장소를 탐색하고 코드를 작성·실행하며 빌드 실패를 스스로 해결하고 풀 리퀘스트를 병합하는 등, 개발자가 매 단계를 지정하지 않아도 스스로 도구와 실행 범위를 선택해 나가는 자율 에이전트를 위한 소프트웨어 개발 전주기 환경 설계를 다룬다. 반면 본 연구는 개발자가 미리 정의한 생성·검증 경계와 처리 경로 내에서 동작하는 범위가 한정된(bounded) 파이프라인을 대상으로, 출력 후보를 사전에 열거하기 어려운 개방형 출력 도메인에서의 환각 통제와 실행 가능성 검증이라는 좁은 문제에 집중한다. 따라서 본 연구의 H = (H_pre, H_post, H_exec)는 OpenAI 사례의 단계 구분을 차용하거나 그로부터 도출된 것이 아니라, 모델 외부 시스템 설계를 통해 신뢰성을 확보한다는 더 넓은 공학적 관점을 공유하는 하나의 사례로서, 본 연구가 다루는 문제에 맞추어 독립적으로 정식화한 구조이다.

## 3. 제안 프레임워크

### 3.1 전체 구조 — 3단계 하네스 엔지니어링

제안 프레임워크는 모델의 가중치를 전혀 수정하지 않고, 모델의 **앞단(입력 통제)·뒷단(사후 가로채기)·외부(런타임 검증)**를 결정론적 규칙과 지식 구조로 감싸는 3단계 하네스 체계로 구성된다.

**정의(하네스 엔지니어링)**: 본 연구는 하네스 엔지니어링을 H = (H_pre, H_post, H_exec) 세 함수의 조합으로 정의한다.
- **H_pre (사전 생성 하네스, Pre-generation Harness)**: LLM이 생성을 시작하기 전에 입력 문맥과 출력 형식을 통제하는 함수. 하이브리드 의도 분류, 온톨로지 기반 문맥 확장, 하이브리드 RAG 검색, 규칙 기반 출력 통제가 여기에 해당한다.
- **H_post (사후 처리 하네스, Post-generation Harness)**: LLM이 생성을 마친 출력을 사후에 검사·교정하는 함수. 어휘 수준 사후 교정과 구조·의미 수준 사후 진단이 여기에 해당한다.
- **H_exec (런타임 실행 하네스, Execution Test Harness)**: H_pre와 H_post를 거쳐 확정된 최종 산출물을 외부 실행 환경(n8n 인스턴스)에 제출하여 실행 가능 여부를 판정하는 함수.

본 연구에서 사용하는 하네스 엔지니어링은 모델 외부의 환경·문맥·제약·검증 체계를 설계한다는 광의의 공학적 관점과 연결되지만(§2.6), 이하의 H = (H_pre, H_post, H_exec)는 개방형 출력 도메인의 생성 통제 및 실행 검증 문제를 위해 본 연구가 정식화한 구체적 구조를 의미한다.

이 세 함수 중 H_pre와 H_post는 사용자에게 전달되는 응답 자체를 형성하는 데 직접 관여하는 **생성 통제(Generation Control)** 계층인 반면, H_exec는 이미 확정된 산출물의 내용을 전혀 바꾸지 않고 그 실행 성패만을 사후적으로 판정하는 **런타임 검증(Runtime Verification)** 계층이다. 즉 H_exec는 생성 성능을 직접 높이는 장치가 아니라 생성 결과를 검증하는 장치이며, 이 구분은 §4의 비교 조건 설계(Tier는 H_pre·H_post의 적용 여부로만 구분되고, H_exec는 모든 Tier에 공통으로 적용되는 측정 장치로 취급된다)와 §4.5의 평가지표(생성 통제 단계에서 형성되는 PCR·SA와, 실행 시점에 별도로 판정되는 EFR의 구분)에 그대로 반영된다.

사용자 질의가 입력되면 **[A] H_pre**(하이브리드 의도 분류 → 온톨로지 기반 문맥 확장 → 하이브리드 RAG 검색 → 규칙 기반 출력 통제 적용 LLM 생성), **[B] H_post**(어휘 수준 사후 교정 → 구조·의미 수준 사후 진단), **[C] H_exec**(실제 n8n 인스턴스 주입을 통한 실행 가능성 검증)의 순서로 처리된다.

#### Part A. 사전 생성 하네스 (Pre-generation Harness)

### 3.2 하이브리드 의도 라우팅 — 순수 규칙 기반의 실패에서 얻은 설계 근거

본 연구는 초기 프로토타입 단계에서 정규식만으로 전체 의도를 분류하는 순수 규칙 기반 설계를 시도하였다. 그러나 "Webhook 노드 설명해줘"(개념 설명)와 "이 워크플로우 어떻게 동작해?"(특정 대상 역분석)처럼 표면적으로 비슷하지만 의미가 다른 문장에서 오분류가 반복되었다. 코드/노드에 대한 자연어 질의는 문맥과 의도를 함께 판단해야 하는 경계 사례가 많기 때문으로 분석된다.

이에 본 연구는 신호의 성격에 따라 판단을 이원화하는 하이브리드 의도 라우터를 설계하였다.

1. **명백한 신호는 규칙으로 즉시 처리한다.** 에러 로그 첨부, 플랫폼 고유 워크플로우 JSON(`"connections"` 키) 첨부, 짧은 꼬리물기 후속 질문은 문장의 의미를 이해할 필요가 없다 — 데이터가 "있는지 없는지"만 보면 되므로 정규식으로 수 ms 내에 확정하고 LLM을 호출하지 않는다.
2. **애매한 자연어는 few-shot 프롬프트를 포함한 LLM으로 분류한다.** 위 3가지에 해당하지 않는 대다수의 질문이 이 경로를 거친다.
3. **키워드 추정은 LLM의 안전망 역할만 한다.** LLM이 애매해서 GENERAL로 회피하거나 호출 자체가 실패했을 때만 가벼운 키워드 추정이 개입해 구제한다. LLM이 정상적으로 구체적인 의도를 반환하면 키워드 추정 결과는 사용되지 않는다.

분류된 의도는 총 6가지(학습 로드맵 생성, 표현식 생성, 워크플로우 설계, 에러 진단, 역분석, 일반 질의응답)이며, 이후 온톨로지 필터링 범위와 출력 통제 스키마를 결정하는 데 사용된다. 본 연구는 "결정론성과 저지연"이 필요한 신호(첨부 데이터 유무)와 "문맥 이해"가 필요한 신호(자연어 의미)를 구분해 서로 다른 판단 기제에 위임하는 것이, 규칙만으로 전체를 처리하는 것보다 개방형 도메인에서 더 견고하다는 설계 시사점을 제공한다.

**LLM 기반 사전 맥락 확장 — 표면적 언급 기반 노드 탐지의 한계에 대한 대응**: 본 연구는 §3.4에서 서술할 온톨로지 노드 탐지가 순수 텍스트 매칭(정확 매칭 + 퍼지 매칭)에 기반한다는 점에서 비롯되는 한계를 발견하였다. 예를 들어 "매일 아침 날씨 확인해서 슬랙으로 알려줘"라는 목적 서술형 질의는 "슬랙"은 텍스트 매칭으로 감지되지만, 실제로 필요한 HTTP Request(날씨 API 호출)나 Schedule Trigger(매일 아침 실행)는 질의문에 해당 명칭이나 유사어가 전혀 등장하지 않으므로 어떤 매칭 단계에서도 감지되지 않는다. 관계 그래프 확장은 이미 감지된 노드에서만 뻗어나가고, 패턴 매칭 역시 최소 2개 이상의 구성 노드가 이미 감지되어 있어야 발동하므로, 이 경우 두 보완 장치 모두 작동하지 않는다.

이에 본 연구는 검색 증강을 위해 질의 대신 LLM이 생성한 가상의 응답을 임베딩하는 HyDE(Hypothetical Document Embeddings)[14]에서 착안하여, 목적 서술형 질의에서 LLM이 필요할 것으로 예상되는 노드를 미리 추정하게 하는 **사전 맥락 확장(Pre-context Expansion)**을 하이브리드 의도 라우터에 통합하였다. 원 기법이 벡터 검색의 임베딩 입력에만 적용되는 것과 달리, 본 연구는 이를 온톨로지의 텍스트 기반 노드 탐지 입력에도 함께 적용한다는 점에서 확장된 응용이다. 구체적으로 §3.2의 LLM 분류 호출은 의도 하나만 반환하는 대신 `INTENT: <의도>` / `HINTS: <예상 노드 목록, 최대 5개>` 두 줄을 함께 반환하도록 프롬프트를 확장하였으며, HINTS는 사용자가 이미 노드명을 언급한 경우에는 비워두고 목적만 서술한 경우에만 채워지도록 지시된다.

이 설계는 두 가지 원칙을 따른다. 첫째, **동일한 LLM 호출에 편승**시켜 별도의 LLM 호출을 추가하지 않으므로, 이미 LLM 분류를 거치는 자연어 경로에서는 추가 지연이 사실상 없다. 명백한 신호 3종으로 규칙 기반 즉시 확정되는 경로(에러 로그·JSON 첨부·꼬리물기)는 원래 LLM을 호출하지 않으므로 이 확장에서도 제외되며, 이 경로들은 이미 구체적 내용(에러 로그, JSON)이 있어 사전 확장의 필요성도 상대적으로 낮다. 둘째, **기존 텍스트 매칭 탐지를 대체하지 않고 보완 신호로 병행**한다 — 원본 질의에 대한 6단계 탐지는 그대로 수행하고, HINTS 텍스트에 대해서도 동일한 탐지 함수를 한 번 더 실행하여 두 결과를 합집합으로 병합한다. 노드명이 명시적으로 언급되는 대다수의 질의는 원본 탐지만으로 이미 충분하므로 이 병행 설계로 인한 손실은 없다.

이 확장이 안전한 이유는 이중 여과 구조에 있다. HINTS에 실재하지 않는 노드명이 포함되더라도 온톨로지 조회(`get_node_def()`)에서 매칭되지 않으므로 자동으로 무해화되며, 실재하지만 이번 요청에는 불필요한 노드가 잘못 포함되더라도 출력 통제(§3.5)와 어휘적 근거 그라운딩 원칙이 최종 생성 단계에서 근거·목적에 맞지 않는 내용을 배제하도록 유도한다. 다만 완전히 부작용이 없다고는 할 수 없다 — 관계 그래프 힌트는 "반드시 참고"라는 강한 지시문으로 프롬프트에 삽입되므로, 불필요한 노드가 감지되면 그에 딸린 힌트가 최종 생성에 약한 편향(가벼운 권유 수준)으로 작용할 가능성은 완전히 배제되지 않는다. 또한 이 메커니즘은 노드 누락 문제를 근본적으로 해결한다기보다 **완화**하는 것으로, 사전 확장 LLM 자체가 실제로 필요한 노드를 정확히 추정하지 못하면 여전히 누락이 발생할 수 있다. 이 완화 효과의 정량적 검증(§4의 330문항 벤치마크 규모)은 §5.3의 향후 연구 과제로 남겨둔다.

**예비 실행 점검(정식 벤치마크 이전의 소규모 스팟체크)**: §4의 통제된 실험과는 별개로, 구현 직후 실제 GPT-4o-mini 호출로 3개 질의에 대한 예비 점검을 수행하였다. "매일 아침 날씨 확인해서 슬랙으로 알려줘"(목적 서술형)에서는 설계 의도대로 HINTS가 "Schedule Trigger, HTTP Request, Slack"을 반환하였고, 실제로 두 노드(Schedule Trigger, HTTP Request)가 사전 확장을 통해서만 추가로 감지되었다 — 원본 질의 텍스트만으로는 감지되지 않았을 노드다. 반면 명시적으로 노드명이 포함된 대조 질의("HTTP Request 노드로 재시도 설정하는 방법")에서는 HINTS가 비워졌고 탐지 결과에도 변화가 없어, 이미 충분한 질의에 부작용을 더하지 않는다는 설계 의도가 확인되었다.

이 점검 과정에서 두 가지를 발견하고 수정하였다. 첫째, 초기 버전에서는 "구글시트에 새 행 추가되면..." 질의에 대해 LLM이 HINTS를 "Trigger"처럼 접미사만 뭉뚱그려 반환해, 실제 필요한 "Google Sheets Trigger"가 온톨로지 사전에 매칭되지 않는 것을 확인하였다 — 이는 본 메커니즘의 회수율이 사전 확장 LLM이 노드명을 얼마나 구체적으로 특정하는지에 좌우됨을 보여주는 사례다. 이에 HINTS 지시문에 "접미사 단독 금지, 서비스/이벤트명까지 포함한 전체 노드명 요구"를 추가하였고, 재점검 결과 "Google Sheets Trigger"가 정상적으로 추가 감지됨을 확인하였다. 둘째, 이 점검 과정에서 본 메커니즘과 무관한 기존 결함도 함께 발견하였다 — 한국어 자모 퍼지 매칭(§3.4)에서 "매일"(매일 아침)이 편집 거리 1 이내라는 이유로 사전 키 "메일"(email, 5자모)에 오매칭되어 무관한 Send Email 노드가 감지되는 문제였다. 전체 퍼지 임계값을 상향하면 "노션"·"수식" 등 다른 5자모 길이 키의 정상적인 오타 교정까지 차단되므로, 본 연구는 실사용 중 발견된 구체적 충돌 사례만을 예외 목록으로 관리하는 점 수정(point fix)을 적용하였다. 두 수정 모두 재실행으로 효과를 확인하였으나, 이는 어디까지나 3건 규모의 예비 점검이며 §4의 통계적으로 설계된 벤치마크를 대체하지 않는다.

### 3.3 5계층 온톨로지 기반 문맥 구조

본 연구의 온톨로지는 다음 5개 레이어로 구성된다(계층 4·5는 두 가지 상태 — 실사용/설계 후 미연결 — 로 나뉘므로 §5.2에서 구현 현황을 별도로 명시한다).

- **레이어 1 (NodeTaxonomy)**: 노드를 역할(트리거/처리/출력/유틸리티)과 출력 형식(JSON/바이너리/없음) 기준으로 분류한다. 전체 노드 공간(723종, §3.8에서 자동 검증)을 다음 3단계로 커버하는 하이브리드 전략을 채택하였다. ① **완전 수동 명세(243개)**: 관계·제약·패턴 정보까지 사람이 직접 작성 — RAG 코퍼스 언급 빈도 상위 185개(수동 노드만으로 RAG 언급의 93.7%를 커버)에, 실사용 빈도가 높다고 판단되는 독립 서비스 58개(예: AWS Lambda, BigQuery, Confluence, Perplexity 등 RAG 코퍼스 빈도 기준이 아닌 실무 판단으로 선별)를 추가로 보강하였다. ② **반자동 관계 연결(321개)**: "XxxTool"(AI 에이전트용 도구 래퍼)·"XxxTrigger" 형태의 노드 중, 기반이 되는 "Xxx" 노드가 이미 온톨로지에 존재하는 경우 — 동일 서비스의 다른 호출 형태라는 n8n 자체의 구조로 보장되는 사실에 근거해 관계 1개를 자동으로 부여한다(예: `slackTool`→`slack`). ③ **순수 자동 생성(159개)**: 관계 없이 명칭 규칙 기반 기본 메타데이터(역할·태그)만 생성한다. ②·③의 원천 노드 목록은 출처가 둘로 나뉜다 — RAG 코퍼스 언급 빈도 3회 이상 기준으로 추출된 268개와, 실제 운영 중인 n8n 인스턴스의 노드 카탈로그(706개, 본문 위 참조)를 전수조사하여 RAG 코퍼스에는 등장하지 않았던 나머지 270개를 추가로 확보한 것이다. 후자는 대부분 AI 에이전트용 Tool 변형 노드와 RAG 코퍼스 구축 이후 n8n에 새로 추가된 노드이며, n8n 내부 테스트·트레이닝 전용 노드는 실제 사용자 워크플로우에 등장하지 않으므로 제외하였다.
- **레이어 2 (RelationGraph)**: 노드 간 동시 사용(COMMONLY_USED_WITH), 선행 요구(PREREQUISITE_FOR), 기능 보완(COMPLEMENTED_BY), 패턴 구성원(PATTERN_MEMBER), 다중 입력 요구(REQUIRES_MULTIPLE_IN), 상호 배제(ANTI_PATTERN_WITH), 기능 대체(REPLACES) 등 7종의 가중치(0~1) 있는 관계를 총 787개 엣지로 정의한다(당초 수동 명세 442개 + 위 반자동 연결 321개 + 신규 수동 보강 24개). 가중치 0.75 이상인 관계만 검색 쿼리 확장에 사용되고, 0.4~0.6대의 낮은 가중치는 주로 안티패턴 경고 힌트 생성에 쓰인다.
- **레이어 3 (PropertyConstraints)**: 파라미터 간 필수(REQUIRES)/충돌(CONFLICTS)/조건부(CONDITIONAL)/권장(RECOMMENDED)/금지(FORBIDDEN) 제약을 총 30개 규칙(25개 고유 노드-속성 쌍)으로 명세한다. 예를 들어 재시도 파라미터(`retryOnFail`)를 설정할 경우 최대 시도 횟수 파라미터(`maxTries`)가 함께 요구되는 연쇄 지식이나, 구버전에서 폐기된 문법(`$item()`)의 사용을 금지하는 규칙이 포함된다.
- **레이어 4 (WorkflowPatterns)**: 검증된 노드 조합 패턴 11개를 라이브러리화하여 모범 사례(best practices)와 안티패턴(anti-patterns)을 동시에 제공한다. 이 계층은 생성 전(RAG 검색 시 힌트 삽입)과 생성 후(검증 리포트에 모범 사례 첨부) 두 시점에서 조회되는 유일한 계층이다.
- **레이어 5 (LearningGraph)**: 17개 학습 개념 간 선행 의존성을 방향성 비순환 그래프(DAG)로 정의하여 커리큘럼 생성에 활용할 목적으로 설계되었다.

### 3.4 온톨로지 기반 RAG 쿼리 확장 및 하이브리드 검색

사용자 질의에서 언급된 노드는 6단계 계층적 감지(정확한 타입 문자열 → camelCase 표기 → 영문 표시명/태그 → 한국어 키워드 사전 → 한국어 자모 퍼지 매칭 → 영문 문자 퍼지 매칭)로 식별된다. 오타가 포함된 경우(예: "웹훅"의 오타 "앱훅")에도 자모 단위 Levenshtein 거리로 정규 노드명을 복원하며, 이 교정 사실은 검색 쿼리 확장뿐 아니라 LLM 시스템 프롬프트에도 "이 단어는 오타이며 별도 개념으로 설명하지 말라"는 지시로 함께 주입되어, 검색과 생성 두 단계에서 동일한 실패(오타를 새로운 개념으로 오인)를 이중으로 방지한다. 이 6단계 감지는 원본 질의뿐 아니라 §3.2의 사전 맥락 확장 힌트에 대해서도 동일하게 수행되며, 두 결과는 합집합으로 병합된다.

감지된 노드를 기준으로 관계 그래프를 탐색해 관련 노드의 표시명과 태그를 검색 쿼리에 추가한 뒤(쿼리 확장), 한국어 질의를 영어 도메인 용어로 확장하는 사전 기반 쿼리 재작성을 거쳐 BM25(희소 검색)와 BGE-M3 임베딩 기반 벡터 검색(밀집 검색)을 병렬 수행하고, RRF(k=60)로 두 결과를 융합한다. 융합된 결과는 의도별로 사전 정의된 data_type 필터(예: EXPRESSION → spec/cli_spec/official_docs)와 개수 제한을 적용해 최종 컨텍스트로 확정된다.

### 3.5 규칙 기반 출력 통제(Output Restriction)를 통한 생성 단계 통제

본 연구는 6가지 의도 중 5가지(학습 로드맵/표현식/워크플로우 설계/역분석/에러 진단)에 대해 의도별로 차별화된 출력 스키마를 출력 통제로 강제한다: 학습 로드맵은 JSON 배열, 표현식 생성과 에러 진단은 정형 마크다운, 워크플로우 설계는 정형 마크다운과 JSON 코드 블록의 혼합, 역분석은 3계층 아코디언 형태의 JSON 배열이다. 일반 질의응답(GENERAL)은 별도의 엄격한 스키마 없이 자유 형식 RAG 기반 응답을 생성한다. 모든 스키마에 공통으로 "컨텍스트 외 내용은 확인되지 않는다고 명시할 것"이라는 어휘적 근거 그라운딩(Lexical Evidence Grounding) 원칙이 적용되어, LLM이 검색되지 않은 파라미터 지식을 자신의 사전 학습 기억에만 의존해 생성하는 것을 프롬프트 수준에서 제한한다.

#### Part B. 사후 처리 하네스 (Post-generation Harness)

### 3.6 사후 교정과 사후 진단의 역할 분리 — 능동적 규칙 기반 교정과 진단적 규칙 기반 검증

본 연구의 핵심적인 설계 확장은 생성 이후 단계에 있다. 규칙 기반 판단 결과를 LLM이 충실히 설명하기만 하면 환각이 발생하지 않는다는 가정은 출력 공간이 폐쇄적인 분류·설명 문제에서는 유효할 수 있으나, 개방형 코드 생성에는 충분하지 않다. 제한된 출력 통제 형식 내에서도 LLM은 파라미터명을 미세하게 잘못 표기하거나(`retryOnFai` ↔ `retryOnFail`), 구조적으로 불완전한 워크플로우(연결이 존재하지 않는 노드를 참조하는 등)를 생성할 수 있다.

본 연구는 이 문제를 성격이 다른 두 개의 사후 계층으로 분리해 대응한다.

**Stage 1 — 규칙 기반 교정(어휘 수준, 능동적 교정)**: 생성된 텍스트에서 표현식 필드명과 JSON 키를 정규식으로 추출한 뒤, 사전에 구축된 유효 파라미터 집합과 대조하여 불일치하는 항목에 대해 Levenshtein 편집 거리[6]를 계산하고, 거리가 임계값(≤2) 이하인 경우 가장 유사한 유효 파라미터로 **자동으로 치환**하는 사후 교정기다. 워크플로우 생성·표현식 생성·에러 패치 세 의도에서만 실행된다.

**Stage 2~4 — 규칙 기반 검증(구조·의미 수준, 진단적 검증)**: 워크플로우 생성·에러 패치 두 의도에서, 그리고 LLM 응답에서 워크플로우 JSON을 실제로 추출할 수 있을 때만 실행되는 4단계 검증이다. ① JSON 구조 자체가 온전한지(연결이 가리키는 노드가 실제로 존재하는지), ② 파라미터 제약(레이어 3)을 만족하는지, ③ 병합 노드의 다중 입력, 웹훅 노드의 응답 노드 짝, Code 노드 내 직접 HTTP 호출 등 하드코딩된 세 가지 안티패턴에 해당하는지, ④ 폐기된 표현식 문법이나 존재하지 않는 노드를 참조하는 표현식이 있는지를 순서대로 진단한다. **중요한 점은, 규칙 기반 검증은 규칙 기반 교정과 달리 위반 사항을 자동으로 수정하지 않고 심각도(오류/경고/정보)와 함께 사용자에게 투명하게 노출하는 데 그친다는 것이다.** 판정 근거를 사용자가 검증할 수 있도록 설명을 함께 제공하는 것은 규칙 기반 시스템의 신뢰도를 높이는 데 기여한다[7].

이러한 역할 분리는 "출력 제한을 통한 예방적(preventive) 환각 억제"를 "탐지 후 자동 교정하는 능동적(corrective) 억제"와 "탐지 후 사용자에게 투명하게 알리는 진단적(diagnostic) 억제"로 세분화하는 것이며, 어휘 수준의 단순 오타는 사용자 개입 없이 즉시 해결하되 구조적·논리적 위반처럼 자동 교정이 오히려 사용자의 의도를 왜곡할 위험이 있는 사안은 판단을 사용자에게 되돌린다는 원칙에 기반한다. 두 계층 모두 발생한 이벤트(교정 내역/위반 목록)를 실시간으로 클라이언트에 공개해 설명 가능성을 확보한다. 이 심각도 분류(ERROR/WARNING/INFO) 체계는 §4.5에서 정의하는 가중 이슈 점수(WIS) 지표의 기반으로 재사용된다.

#### Part C. 런타임 실행 하네스 (Execution Test Harness)

### 3.7 실행 가능성 검증 — 캔버스 직접 주입과 API 기반 자동화 하네스

생성된 워크플로우 코드는 자연어 설명에 머무르지 않고, 실 서비스 환경에서는 Chrome 확장을 경유해 실제 편집기 캔버스에 직접 주입되어 동작 여부를 즉시 확인할 수 있다(`server/workflow.py`의 `/api/workflow/inject`). 별도로 `server/workflow.py`에는 `docker-compose.yml`에 포함된 n8n 인스턴스(`n8nio/n8n`)의 Public REST API(`POST /api/v1/workflows`)에 직접 요청하는 `/api/workflow/remote-inject` 엔드포인트가 실제로 구현되어 있으며, n8n의 엄격한 스키마 검증(ajv)을 LLM 출력이 통과하지 못하는 문제(부가 필드 포함 등)에 대응하기 위한 필드 정제 로직도 포함한다.

이 엔드포인트는 워크플로우 생성(스키마 검증 통과) 성공 여부에 더해, `verify_execution` 옵션이 켜졌을 때 실제 트리거와 런타임 실행 결과(성공/오류) 확인까지 수행한다. n8n Public API는 임의 트리거 타입의 워크플로우를 API 키만으로 즉시 실행하는 엔드포인트를 제공하지 않는다(발행/평가용 test-run만 존재하며, 후자는 전용 Evaluation Trigger 노드가 필요해 일반 생성 워크플로우에는 적용할 수 없다). 따라서 API 키만으로 실제 실행 결과까지 확인 가능한 유일한 경로로, 웹훅 트리거 워크플로우를 발행(publish)한 뒤 그 웹훅을 직접 호출하고 실행 목록을 폴링하는 방식을 채택하였다. 웹훅 트리거가 아닌 워크플로우(수동/스케줄/앱별 트리거)는 API 키만으로 즉시 실행을 트리거할 수 없으므로 스키마 검증까지만 자동 판정하고, 그 사실을 응답에 `execution_note`로 투명하게 표시한다. 또한 실행 검증은 워크플로우 내 노드의 실제 부수효과(메시지 발송 등)를 유발할 수 있으므로, 기존 호출과의 하위호환을 위해 기본값 false인 opt-in 파라미터로 노출하였다.

이 기능은 실제 배포 환경에 반영한 뒤 다음과 같은 라이브 검증을 수행하였다. (1) 수동으로 구성한 성공/실패 웹훅 워크플로우 각 1건에 대해 실제 실행 성공(`status: success`)과 실행 실패(`status: error`, 오류 메시지까지 정확히 추출)가 각각 올바르게 판정됨을 확인하였다. (2) 비웹훅 트리거(Manual Trigger) 워크플로우에서 스키마 검증까지만 수행하고 정직하게 `execution_note`를 반환함을 확인하였다. (3) `verify_execution`을 생략한 기존 호출 방식이 하위호환되어 그대로 동작함을 확인하였다. (4) 실제 프로덕션 파이프라인으로 생성한 워크플로우 2건을 동일한 방식으로 검증한 결과, 한 건은 노드가 참조하는 자격 증명(Slack API)이 인스턴스에 등록되어 있지 않아 발행 단계에서 거부되었고, 다른 한 건은 스키마 검증은 통과했으나 LLM이 `n8n-nodes-base.code`(신규 Code 노드) 타입에 구버전 Function 노드의 파라미터 키인 `functionCode`를 사용해(신규 노드가 실제로 요구하는 키는 `jsCode`) 실행 시점에 내부 assertion 오류로 실패하였다 — 이는 **스키마 검증(ajv) 단계에서는 전혀 드러나지 않고 실제 실행 시점에만 드러나는 결함 유형**으로, 본 실행 검증 기능이 추가되기 전에는 "생성 성공"으로 잘못 판정되었을 사례다.

## 4. 평가 방법론

본 장은 데이터 수집 이전에 가설·표본크기·채점 절차·통계 분석 계획을 사전에 확정하는 준(準)사전등록(quasi-preregistration) 방식으로 설계하였다. 이는 결과가 나온 뒤 분석 방법을 유리하게 선택하는 것을 방지하고, 평가 자체의 재현성과 통계적 방어력을 확보하기 위한 본 연구 고유의 설계 원칙이다.

### 4.1 연구 가설

- **H1 (주가설)**: 제안 프레임워크 적용 상태(Tier 3)는 Raw LLM(Tier 1) 대비 파라미터 정합률(PCR)이 통계적으로 유의하게 높다.
- **H2 (주가설)**: Tier 3는 Tier 1 대비 가중 환각 점수(WIS)가 통계적으로 유의하게 낮다.
- **H3 (부가설)**: Tier 3(H_pre+H_post)는 H_pre만 적용한 Tier 2 대비 실행 가능률(EFR)이 통계적으로 유의하게 높다 — 즉 사전 생성 하네스(의도 라우팅·온톨로지·RAG·출력 통제)만으로는 부족하며, 사후 처리 하네스(어휘 교정·구조 검증)가 추가적 효과를 가진다.
- **H4 (일반화 가설)**: H1·H2에서 관측된 개선 효과는 GPT-4o뿐 아니라 Gemini에서도 재현되며, Tier×Model 상호작용은 통계적으로 유의하지 않다(개선 효과가 모델에 의존하지 않음).
- **H5 (탐색적 가설)**: 규칙 기반 교정기의 편집 거리 임계값(≤2) 교정 성공률(RCR)은 파라미터명 길이와 유의한 상관관계를 가진다 — 임계값 설계의 타당성을 사후적으로 점검한다.

### 4.2 결정론적 자동 채점과 인간 판정의 분리

본 연구의 평가 지표는 채점 방식에 따라 두 그룹으로 명확히 분리된다. 이는 "환각률 측정이 다시 주관적 환각(LLM/사람의 판단)에 의존한다"는 순환성 문제를 최소화하기 위함이다.

**결정론적 자동 채점 지표 (PCR, EFR, SA)**: `reg_validator.py`의 파라미터 추출 정규식과 동일한 로직을 독립적인 오프라인 채점 스크립트로 재구현하여, LLM 응답에서 파라미터명을 추출하고 n8n 공식 스펙(`n8n_properties_spec.txt`)의 유효 속성 집합과 문자열 단위로 대조한다. 이 채점은 사람이나 LLM의 판단 없이 100% 재현 가능하다. EFR은 §3.7에서 서술한 n8n Public REST API 기반 하네스로 자동 판정하며, 웹훅 트리거 워크플로우는 실제 발행·트리거·실행결과까지 확인하고 그 외 트리거 타입은 생성/스키마 검증 통과 여부까지 판정한다(플랫폼 API 제약에 따른 범위이며, 채점 시 트리거 타입별로 판정 근거가 다르다는 점을 명시해야 한다). SA는 의도별 출력 통제 스키마(§3.5)에 대한 JSON 스키마 검증기로 자동 판정한다.

**중요한 설계 상 유의점**: Tier 3는 규칙 기반 교정기가 사후 교정을 수행하므로, 최종 응답만을 채점하면 "이미 고쳐진 결과"만 보게 되어 Tier 1·2와의 비교가 왜곡될 수 있다. 이에 본 연구는 Tier 3에 대해 PCR과 WIS를 **PCR_raw / WIS_raw(규칙 기반 교정 적용 전, LLM 원본 출력)**와 **PCR_final / WIS_final(규칙 기반 교정·규칙 기반 검증 적용 후, 사용자에게 실제 전달되는 값)**로 이중 측정한다. PCR_raw는 Tier 1·2와 동일 조건에서 "생성 자체의 품질"을 비교하기 위한 것이고, PCR_final은 "최종 사용자 체감 품질"을 비교하기 위한 것이다. 이 이중 측정 설계는 사후 교정 계층이 있는 시스템을 사후 교정이 없는 baseline과 비교할 때 발생하는 착시(사후 교정이 원래 생성 품질을 가려버리는 문제)를 방지한다.

**인간 판정이 필요한 지표 (환각 유형 세분류)**: 파라미터명 대조로 잡히지 않는 "근거 없는 능력 창작형 환각"(예: 존재하지 않는 노드 기능을 있다고 서술, 근거 없는 워크플로우 동작 방식 설명)은 결정론적으로 채점할 수 없으므로 §4.6의 근거 대조 기반 라벨링 프로토콜로 판정한다.

### 4.3 벤치마크 데이터셋 구성 및 표본 크기 산정

**표본 크기 산정(검정력 분석)**: 1차 지표인 PCR의 두 비율(Tier 1 대략 50%, Tier 3 대략 70%로 사전 추정, 20%p 차이를 최소 검출 효과로 설정) 차이를 유의수준 α=0.05(양측), 검정력 1-β=0.80으로 검출하기 위한 독립표본 비율차 검정 표본크기 공식은 다음과 같다.

```
n = (z_{α/2} + z_β)² · [p1(1-p1) + p2(1-p2)] / (p1-p2)²
  = (1.96 + 0.84)² · [0.50·0.50 + 0.70·0.30] / (0.20)²
  = 7.84 · 0.46 / 0.04 ≈ 90.2 → 조건당 최소 91건
```

이는 독립표본 근사이며, 본 실험은 동일 질의를 세 Tier에 반복 적용하는 대응표본(paired) 설계이므로 실제 필요 표본은 이보다 적거나 같다 — 즉 위 산정치는 보수적 상한이다. 본 연구는 의도 유형(워크플로우 설계/표현식 생성/에러 진단) 3종에 걸쳐 각 90건씩 총 270건의 핵심 벤치마크 질의를 구성하여 산정된 최소 표본을 충족한다.

**질의 출처의 이원화(생태학적 타당성 확보)**: 연구자가 직접 고안한 시나리오만으로는 실제 사용 맥락을 온전히 반영하기 어렵다. 본 연구는 질의의 약 40%를 n8n 공식 커뮤니티 포럼·GitHub 이슈 등 실제 사용자 질문에서 수집·재구성하여, 연구자 편향(researcher bias)을 줄이고 실제 사용 맥락과의 외적 타당성을 높인다는 것을 설계 원칙으로 한다. **다만 §4.10에서 보고하는 N=330 실행은 이 이원화 설계를 적용하지 않고 질의 전량을 체계적 자동 생성으로만 구성하였다** — 이는 실행상의 단순화이며 설계 자체의 변경은 아니다. 커뮤니티 수집을 포함한 완전한 이원화 벤치마크의 실행은 향후 과제로 남기며, 이로 인한 외적 타당성 한계는 §4.8에서 별도로 논의한다.

**적대적/경계 사례 하위셋**: 핵심 270건에 더해, 규칙 기반 교정기·규칙 기반 검증기의 처리 경계를 의도적으로 겨냥한 적대적 질의 60건(의도 유형별 20건)을 추가로 구성한다 — 편집 거리 2를 초과하는 파라미터 오타, 폐기된 문법과 신규 문법이 혼재된 질의, 온톨로지 자모 퍼지 매칭의 임계값 경계에 걸치는 오타 노드명 등을 포함한다. 총 벤치마크 규모는 **330문항**이다.

### 4.4 비교 조건 매트릭스 — Tier × Model

각 Tier는 §3.1에서 정의한 H_pre·H_post의 적용 여부만으로 구분되며, H_exec(런타임 실행 하네스)는 생성에 관여하지 않는 측정 장치이므로 세 Tier 모두에 공통으로 적용되어 EFR을 산출한다. Tier 2를 "온톨로지 문맥만 적용"이 아니라 **H_pre 전체**(하이브리드 의도 라우팅 + 온톨로지 + 하이브리드 RAG + 출력 통제)로 정의하는 것이 중요하다 — 그래야 Tier 2→Tier 3 구간의 차이가 온전히 H_post 하나의 순효과로 해석되며, 의도 라우팅이나 출력 통제의 효과가 이 구간에 섞여 들어가는 교란을 막을 수 있다.

| Tier | 구성 | H_pre | H_post | H_exec |
|---|---|---|---|---|
| Tier 1 — Raw LLM (baseline) | 프레임워크 미적용, 사용자 질의 직접 입력 | 미적용 | 미적용 | 공통 측정 |
| Tier 2 — LLM + H_pre | 하이브리드 의도 라우팅 + 온톨로지 힌트 + 하이브리드 RAG + 규칙 기반 출력 통제 | 적용 | 미적용 | 공통 측정 |
| Tier 3 — LLM + H_pre + H_post (제안 프레임워크 전체) | Tier 2 구성 + 규칙 기반 교정(어휘) + 규칙 기반 검증(구조·의미) | 적용 | 적용 | 공통 측정 |

이 3단 구조를 **GPT-4o(주 모델, 전체 330문항×3 Tier)**와 **Gemini(교차검증 모델, 비용을 고려해 층화 부표본 90문항×3 Tier)**에 각각 적용한다. Gemini 조건은 전체 표본이 아닌 부표본을 사용하지만, 의도 유형별 균형을 유지하도록 층화 추출하여 §4.7의 Tier×Model 상호작용 검정에 필요한 최소 검정력을 확보한다. 총 실험 조건은 (330×3) + (90×3) = 1,260회 응답이다. 실험 자원이 더 확보되는 경우 Tier 2를 "H_pre 중 온톨로지·RAG만" vs "H_pre 전체"로 한 단계 더 세분화하여 4단 비교로 확장할 수 있으나, 본 연구는 현재 자원 범위에서 H_pre/H_post의 순효과를 분리하는 데 필요한 최소 단위인 3단 비교를 기본 설계로 채택한다.

### 4.5 평가 지표

- **PCR (Parameter Conformance Rate, 파라미터 정합률)**: §4.2 기준 결정론적 자동 채점. Tier 3는 PCR_raw/PCR_final 이중 보고.
- **WIS (Weighted Issue Score, 가중 이슈 점수)**: §3.6의 ValidationSeverity 체계를 재사용해 ERROR=3, WARNING=2, INFO=1의 가중치를 부여하고, 한 응답에서 탐지된 모든 이슈의 가중치 합을 응답당 점수로 산출한다(낮을수록 우수). 단순 이분법적 "환각 있음/없음"보다 심각도 차이를 반영하는 세분화된 지표다.
- **HR (Hallucination Rate, 환각 발생률, 인간 판정)**: 파라미터명 오류로 환원되지 않는 근거 없는 서술이 포함된 응답의 비율. 본 연구는 결정론적으로 채점 가능한 부분(파라미터/문법 오류)을 PCR·WIS로 분리했으므로, HR은 순수하게 인간 판정이 필요한 잔여 범주만을 다룬다.
- **EFR (Execution Feasibility Rate, 실행 가능률)**: §3.7의 자동화 하네스로 결정론적 채점.
- **SA (Structural Alignment, 구조 정합도)**: 의도별 출력 통제 스키마(§3.5)가 요구하는 필수 구조 요소가 누락 없이 생성되었는지를 JSON 스키마 검증기로 결정론적 채점. Raw LLM(Tier 1)은 출력 통제 스키마가 없으므로 "후속 파서가 기계적으로 처리 가능한 형태인가"를 동일 채점기로 평가한다.
- **RCR (Rule-based Correction Rate, 어휘 교정 성공률, Tier 3 전용)**: 규칙 기반 교정기가 감지한 오류 중 실제로 올바른 값으로 교정된 비율. 편집 거리 임계값을 벗어난 폴백 사례 비중도 함께 보고하며, H5의 상관분석 대상이다.
- **위반 탐지율(Detection Rate, 규칙 기반 검증기, Tier 3 전용)**: 구조·제약·패턴·표현식 위반 중 실제로 탐지·보고된 비율.
- **DRR (Decision Reproducibility Rate, 결정 재현성 비율)**: 동일 질의를 동일 조건에서 온도(temperature) > 0으로 k=3회 반복 실행했을 때, PCR 판정(정합/부정합)이 3회 모두 일치하는 질의의 비율.
- **비용·지연 지표**: 응답당 평균 토큰 사용량과 종단 지연시간(E2E-RT)을 Tier별로 병기하여, 정확도 개선이 어느 정도의 비용·지연 증가를 수반하는지 비용-정확도 트레이드오프를 함께 보고한다.

### 4.6 근거 대조 기반 라벨링 프로토콜 (Reference-grounded Labeling)

HR 판정 대상은 파라미터·문법 오류로 환원되지 않는 "근거 없는 능력 창작형 환각"뿐이므로(§4.2), 이 판정은 n8n 도메인 지식을 요구하는 주관적 평가가 아니라 **시스템이 실제로 검색·참조한 근거 문서와 응답을 대조하는 충실성(faithfulness) 검사**로 설계한다. 각 질의-응답 쌍에 대해 평가자에게는 (1) LLM 응답 전문(단, 결정론적으로 이미 판정되는 파라미터·문법 오류 구간은 사전 표시), (2) 하이브리드 RAG가 해당 질의에서 실제로 검색해 프롬프트에 삽입한 근거 청크(§3.4, 시스템이 로그로 남기는 참조 문서 원문)가 함께 제시되며, 평가자는 "응답이 제시된 근거 자료에 없는 노드 기능·동작 방식을 주장하고 있는가?"라는 단일 폐쇄형 질문에 예/아니오/판단보류 3지선다로만 답한다. 모든 응답은 Tier·모델 식별 정보를 제거하고 무작위 순서로 재배열한 뒤 익명 ID로 제시한다(단일 블라인드).

이러한 설계는 판정의 정확성을 "평가자가 n8n을 얼마나 아는가"가 아니라 "제시된 근거와 응답을 얼마나 정확히 대조했는가"에 의존하게 하므로, **n8n 도메인 지식이 없는 평가자도 짧은 루브릭(판정 기준 1쪽 + 예시 3건)만으로 신뢰성 있게 수행할 수 있다.** 이는 본 연구가 소규모 연구 인력으로도 실행 가능하도록 의도적으로 설계한 부분이다.

**평가자 구성과 표본 크기**: 본 연구는 주 평가자 1인(연구 수행자)과 도메인 지식이 없는 보조 평가자 1인으로 구성된 2인 체제를 채택한다. 두 평가자는 **동일한 문항 집합**(분담이 아닌 전원 중복 라벨링)에 대해 위와 동일한 근거 대조 루브릭으로 독립 라벨링한다. 필요한 중복 표본 크기는 Cohen's κ의 대표본 분산 근사식(Fleiss, Cohen & Everitt, 1969)에 기반해 산정한다: 목표 κ≈0.65, 예상 환각 유병률(prevalence) 15~25%(Tier 3는 이미 결정론적 필터와 규칙 기반 교정을 거친 뒤이므로 잔여 환각 비율이 낮음) 조건에서 95% 신뢰구간 반폭을 ±0.15로 확보하려면 **N≈50건**이 필요하며, 이는 소규모 평가자 간 신뢰도 연구에서 통용되는 정밀도-표본 관계[13]와도 부합한다. 이 50건은 의도 유형(워크플로우 설계/표현식 생성/에러 진단) 3종에 걸쳐 층화 추출하며, 카파 산출에만 쓰이는 것이 아니라 조정(합의) 후 그대로 실제 HR 분석의 정식 라벨로도 사용된다. 두 평가자 간 불일치 문항(경험상 전체의 15~20%, 약 8~10건 수준)은 두 평가자가 재논의하여 합의하거나, 합의가 안 될 경우에 한해 제3의 조정자(지도교수 등)에게 해당 소수 문항만 판정을 요청한다. Cohen's κ는 Landis & Koch[11]의 해석 기준에 따라 κ≥0.60("substantial agreement")을 목표 임계값으로 보고한다. 부득이하게 보조 평가자를 확보하지 못할 경우에도 주 평가자 단독 라벨링만으로 본 프로토콜은 유효하며, 이때는 §4.8에서 단일 평가자 한계로 명시한다.

**순수 LLM-judge 단독 채점을 채택하지 않은 이유**: HR 판정 과제는 폐쇄형 근거 대조 질문이므로, 원칙적으로 LLM 판정자가 1,260건 전량을 채점하고 사람은 전혀 개입하지 않는 것도 기술적으로는 가능하다. 그러나 이 경우 두 가지 문제가 발생한다. 첫째, LLM 판정자는 응답의 형식적 정형성에 관대하게 반응하는 경향이 보고되어 있어[12], 본 연구의 출력 통제 스키마로 정제된 Tier 3 응답이 실제로는 근거를 벗어난 내용을 포함하더라도 형식이 정돈되어 있다는 이유만으로 "근거에 부합"으로 과대평가될 위험이 있다. 둘째, "LLM이 LLM 출력을 채점"하는 구조는 판정자 자체의 신뢰도를 뒷받침할 외부 기준이 없으면 순환적(self-referential)이 되어, HR 지표 전체가 검증되지 않은 판정자에 의존하게 된다. 이에 본 연구는 LLM-judge가 1,260건 전량을 1차 채점하되, 별도로 확보한 N≈50건의 인간 판정 표본으로 판정자 자체의 신뢰도(LLM-인간 일치도)를 검증하는 구조를 채택한다 — 즉 인간 라벨링 50건의 목적은 "n8n 지식을 확인"하는 것이 아니라 "판정자를 신뢰해도 되는지 확인"하는 것이다.

**LLM-judge 교차검증**: 대규모 벤치마크(1,260건)를 전량 인간이 라벨링하는 것은 2인 체제에서도 부담이 크므로, LLM-as-judge를 1차 선별 도구로 병행한다[12]. 판정 대상 모델(GPT-4o)을 판정자로 사용할 경우 자기 선호 편향(self-preference bias)이 보고된 바 있으므로[12], 판정자는 비교 대상에 포함되지 않은 별도 모델을 사용한다. 전체 응답에 대해 LLM 판정을 우선 수행하고, 위와 동일한 층화 무작위 표본(N≈50건)에 대해 두 인간 평가자가 동일한 근거 대조 루브릭으로 교차 검증하여 LLM-인간 판정 간 일치도를 별도로 보고한다. 일치도가 낮게 나타날 경우 해당 범주는 인간 평가로 재검증한다.

### 4.7 통계 분석 계획

모든 분석은 유의수준 α=0.05를 기준으로 하되, 다중 비교로 인한 오류를 통제하기 위해 Holm-Bonferroni 보정을 적용한다.

- **1차 분석(H1, H2, H3)**: 동일 질의가 여러 Tier에서 반복 측정되는 구조를 반영하여, 질의(query)와 평가자(rater)를 무작위 효과(random effect)로 포함하는 일반화 선형 혼합모형(GLMM)을 적용한다 — PCR·EFR·SA와 같은 비율형 지표에는 이항 로지스틱 링크를, WIS와 같은 연속형 지표에는 항등 링크를 사용한다. Tier를 고정 효과로 두어 Tier 계수의 유의성을 검정한다.
- **강건성 확인(robustness check)**: GLMM과 별개로, 동일 질의에 대한 Tier 간 쌍대 비교에는 이분형 지표(EFR 성공/실패, HR 있음/없음)에 대해 McNemar 검정[9]을, 순위형·비정규 분포 지표(WIS)에는 Wilcoxon 부호순위 검정[10]을 병행하여 GLMM 결과와 교차 검증한다.
- **일반화 검정(H4)**: GLMM에 Tier×Model 상호작용항을 추가하여, 상호작용이 유의하지 않음(p>0.05, 사전 정의된 동등성 마진 내)을 통해 개선 효과가 모델 전반에 일반화됨을 검정한다.
- **탐색적 분석(H5)**: RCR과 파라미터명 문자열 길이 간 Spearman 순위상관을 계산한다.
- **효과크기와 신뢰구간**: 모든 주요 비교에 대해 승산비(odds ratio) 또는 Cohen's h(비율 차이의 효과크기), 대응표본 순위-이연 상관(matched-pairs rank-biserial correlation, Wilcoxon용)을 함께 보고하며, 모든 점추정치에는 부트스트랩(10,000회 재표본) 95% 신뢰구간을 병기한다.

### 4.8 위협 요인(Threats to Validity)

- **내적 타당성**: LLM 응답의 확률적 변동성(같은 질의라도 실행마다 다른 출력)을 DRR로 별도 정량화하여 통제한다. 판정자 편향은 §4.6의 블라인드 처리, 근거 대조 기반 폐쇄형 질문 설계, 비교 대상 외 모델을 판정자로 사용하는 조치로 완화한다.
- **외적 타당성**: 결과는 n8n 도메인에 한정되며, 다른 노코드 플랫폼으로 일반화되는지는 확인되지 않는다. 모델 범위에서도, §4.10에서 실제로 실행한 N=330 본실험은 GPT-4o 단일 모델에 한정되어 있어 Gemini나 오픈소스 모델로의 일반화(H4)는 검증되지 않았다. 벤치마크 구성 측면에서도, §4.3은 질의의 약 40%를 실제 커뮤니티 질문에서 수집하는 설계를 명시하지만 §4.10의 N=330 실행에서는 이를 적용하지 않고 전량을 체계적 자동 생성으로 구성하였다(트리거×액션 조합, 서비스 특화, 적대적 사례) — 따라서 본 실행 결과는 연구자가 설계한 질의 분포에 대한 것이며, 실제 사용자의 질의 분포·표현·난이도를 완전히 대표한다고 볼 수 없다. 커뮤니티 수집을 포함한 이원화 벤치마크의 실행과 그에 따른 결과 재검증은 향후 과제다.
- **구성 타당성**: PCR·HR·EFR·SA·WIS가 "응답 품질"이라는 구성개념을 완전히 포괄하지는 못한다. 특히 사용자 유용성·만족도와 같은 주관적 가치는 본 지표 체계에서 다루지 않으며, 이는 향후 연구(§5.3)의 사용자 평가로 보완한다.
- **신뢰성**: §4.6의 2인 체제에서 산출한 평가자 간 신뢰도(κ)를 명시적으로 보고하고 목표 임계값(κ≥0.60)을 사전에 설정함으로써 라벨링 신뢰성을 사후 검증 가능하게 한다. LLM-judge의 자기 선호 편향과 형식 관대성 편향은 비교 대상 외 모델 사용과 N≈50건 인간 교차검증으로 완화한다. 부득이하게 단일 평가자 체제로 축소될 경우, HR 라벨링의 신뢰성 근거는 §4.6의 근거 대조 기반 폐쇄형 루브릭과 LLM-judge와의 판정 일치도만으로 축소되며, 이는 다인 평가자 간 신뢰도의 완전한 대체재는 아니라는 점을 본 연구는 명시적으로 인정한다.

### 4.9 파일럿 실행 결과 (N=30)

§4.1~§4.8에서 설계한 평가 방법론을 실제로 실행 가능한지 검증하기 위해, 본실험(330문항) 착수 전 예비 파일럿을 수행하였다. 범위는 다음과 같이 명시적으로 한정한다: WORKFLOW_BUILD 인텐트 30문항(단순 10·보통 10·복잡 5·적대적/경계 5, §4.3의 난이도 구분을 축소 적용), GPT-4o 단일 모델(Gemini 교차모델 H4는 API 키 미보유로 제외), HR(근거 대조 기반 인간 판정)과 DRR(k=3 반복 재현성)은 각각 별도 웹 도구 구축과 본실험으로 유보하였다. 실행 코드는 `eval/run_pilot.py`(벤치마크 실행)·`eval/analyze_pilot.py`(통계 분석)·`eval/benchmark_pilot.py`(문항 정의)에 재현 가능한 형태로 보존하였으며, 세션 종료와 무관하게 지속되는 백그라운드 프로세스로 실행하고 문항 1건이 끝날 때마다 즉시 결과를 저장해 중단 시에도 진행분이 유실되지 않도록 설계하였다.

**Tier1/2/3 생성 방식**: Tier 1은 온톨로지·RAG·출력 통제 없이 GPT-4o를 직접 호출한 raw 응답이다. H_post(규칙 기반 교정·검증)는 현재 구현상 응답에 교정안을 제시할 뿐 실행되는 JSON을 자동으로 재작성하지는 않으므로(교정 적용 여부는 최종적으로 프런트엔드/사용자 몫), Tier 2와 Tier 3는 동일한 H_pre 생성 결과를 공유하되 채점 방식만 다르다 — Tier 2는 교정 적용 전(raw) 상태를, Tier 3는 REG가 제시한 교정을 실제로 적용한 사후 상태(PCR_final, EFR_corrected)를 채점한다.

**요약 지표**:

| 지표 | Tier 1 (Raw LLM) | Tier 2 (H_pre) | Tier 3 (H_pre+H_post) |
|---|---|---|---|
| PCR (평균) | 0.818 | 0.831 (raw) | 0.838 (final) |
| PCR 완전정합률(=1.0인 문항 비율) | 26.7% | — | 50.0% |
| SA (평균) | 1.000 | 1.000 | 1.000 |
| WIS (평균, 낮을수록 우수) | 0.100 | — | 0.333 |
| EFR (비율) | 96.7% | 100% (raw) | 100% (corrected) |
| RCR (평균) | — | — | 4.4% |

**가설 검정 결과** (Wilcoxon 부호순위·McNemar, Holm-Bonferroni 보정, 부트스트랩 95% CI 10,000회):

- **H1(PCR)**: Tier1 대비 Tier3_final 평균 차이 +0.020(95% CI [−0.074, 0.100]), Wilcoxon p=0.242(보정 후 0.539) — N=30에서는 유의하지 않음. 다만 PCR을 "완전정합(모든 파라미터가 유효)" 여부로 이분화한 강건성 검정에서는 26.7%→50.0%로 거의 두 배 증가하였고(Cohen's h=0.486, 중간~큰 효과크기), McNemar p=0.092로 유의수준에 근접하는 고무적인 신호를 보였다.
- **H2(WIS)**: 평균 차이 +0.233(Tier3가 오히려 높음, 즉 표면적으로는 악화), Wilcoxon p=0.180(보정 후 0.539). **이 결과는 가설이 예측한 방향과 반대이므로 원인을 개별 문항 단위로 직접 조사하였다.** 30문항 중 WIS가 다른 문항은 단 2건(wb01, wb15)뿐이었다: wb01은 Tier3가 `responseMode: responseNode`를 설정하면서도 이를 위해 필요한 `Respond to Webhook` 노드를 추가하지 않은 사례, wb15는 Tier3의 Merge 노드 입력 연결이 요구되는 2개에 못 미친 사례로, 둘 다 **규칙 기반 검증기가 실제로 존재하는 구조적 결함을 정확히 탐지한 진짜 양성(true positive)**이었다. 반면 Tier1(raw)의 동일 문항 응답은 애초에 이 두 검증기가 점검하는 패턴 자체를 사용하지 않아(예: `responseMode: lastNode` + 별도 응답 노드 조합처럼 더 단순한 구성을 택함) 점검 대상에서 벗어났을 뿐이다. 즉 WIS가 더 높게 나온 것은 H_pre가 유도하는 특정 생성 패턴에서 H_pre 자체가 만든 내적 비일관성을 H_post가 잡아낸 결과이며, "프레임워크가 결함을 더 많이 만든다"는 의미가 아니라 "현재 규칙 기반 검증기의 점검 범위(§5.3에서 이미 보고한 3종 하드코딩 검사)가 좁아 30문항 중 2건에서만 신호가 발생했다"는 표본 크기·검증기 커버리지의 한계로 해석하는 것이 정확하다.
- **H3(EFR)**: Tier2(raw) 100% vs Tier3(corrected) 100%로 완전히 동일(McNemar p=1.0, Cohen's h=0.0) — 두 조건 모두 EFR 천장 효과(ceiling effect)에 도달해 차이가 관측되지 않았다. RCR 평균이 4.4%로 낮아(GPT-4o가 이미 파라미터명을 비교적 정확히 생성해 교정이 발생하는 사례 자체가 드묾) 교정으로 인한 EFR 개선 여지가 애초에 작았고, 벤치마크 문항 대부분이 스키마 검증까지만 판정되는 비웹훅 트리거였다는 점도 천장 효과에 기여하였다.
- **H5(RCR vs 길이)**: n=15(교정이 1건이라도 발생한 문항), Spearman ρ=0.031, p=0.912 — 상관관계 없음. 다만 이는 문항 단위 평균 길이 근사치이며 개별 토큰 단위 상관은 아니라는 §4.7 설계와의 괴리를 인정한다(원자료 보존은 본실험 범위).

**파일럿의 한계**: N=30은 §4.3에서 산정한 최소 표본(조건당 91건, 본실험 330건)에 크게 못 미쳐 검정력이 낮다 — 위 p값들은 파이프라인이 의도대로 작동하는지 확인하는 예비 신호이지 확증적 결론이 아니다. GLMM(질의를 무작위효과로 포함하는 모형)은 N=30에서 수렴이 불안정해 생략하고 McNemar·Wilcoxon 강건성 검정만 수행하였다. 이러한 한계에도 불구하고, 본 파일럿은 (1) §4의 평가 방법론이 실제로 실행 가능함을 실증하고, (2) PCR 완전정합률에서 유의수준에 근접한 고무적 신호를 확인했으며, (3) WIS 역전이라는 반직관적 결과를 원인 수준까지 추적해 규칙 기반 검증기의 커버리지 한계라는 기존에 알려진 문제(§5.3)와 정합적으로 설명할 수 있음을 보였다는 점에서, 본실험(N=330) 착수의 실증적 근거를 제공한다.

### 4.10 본실험 결과 (N=330)

§4.9의 N=30 파일럿이 파이프라인 전체(생성·채점·통계 분석)가 오류 없이 작동함을 확인한 뒤, 동일한 채점 프로토콜을 전혀 변경하지 않고("프로토콜 동결") 표본만 330개로 확장한 본실험을 실행하였다. 범위는 파일럿과 동일하게 WORKFLOW_BUILD 인텐트·GPT-4o 단일 모델·HR/DRR/Gemini 교차모델 제외로 한정하였으며, 다음 두 가지 차이가 있다. 첫째, §4.3이 요구하는 3개 인텐트(워크플로우 설계/표현식 생성/에러 진단) 균등 배분 대신 WORKFLOW_BUILD 단일 인텐트에 330문항을 전부 배정하였다 — EXPRESSION·ERROR_PATCH는 PCR/EFR 정의 자체가 워크플로우 JSON 구조에 결합되어 있어 별도 채점 로직 설계가 필요하며, 이는 "파일럿에서 검증된 프로토콜을 그대로 유지"한다는 원칙과 상충하므로 향후 확장 과제로 남긴다. 둘째, §4.3의 "질의의 약 40%를 실제 커뮤니티에서 수집"하는 이원화 설계 대신, 트리거 20종×액션 20종의 체계적 조합과 서비스 특화·적대적 사례를 코드로 생성하는 완전 합성 벤치마크를 사용하였다(`eval/benchmark_330.py`) — 이는 §4.8의 외적 타당성 한계로 정직하게 보고한다. 실행은 세션 종료와 무관하게 지속되는 백그라운드 프로세스로 이루어졌으며(`eval/run_full.py`), 파일럿에서 발견한 n8n 부하 문제 재발을 막기 위해 문항 10건마다 n8n 헬스체크와 페이싱(문항 간 2초 지연)을 추가하였다. 330문항 전체를 오류 0건으로 완주하였다(총 소요 약 2시간 18분).

**실행 중 발견·수정한 추가 결함**: 파일럿 결과를 검토하던 중, Tier2/3에서 실제로 웹훅 노드를 생성했음에도 실행 검증이 "타임아웃"으로 오판정되는 사례(§4.9의 wb01·wb26)를 발견하였다. 원인은 `_verify_execution()`의 고정 8초 폴링이었다 — 반복적인 publish/trigger/poll이 누적되며 n8n이 부하 상태에 놓였을 때는 실제로 성공한 실행조차 8초 안에 기록되지 않았다. 폴링을 간격을 점증시키며 최대 약 28초까지 대기하도록 수정·배포하였다(§3.7). 본실험에서 이 수정이 실제로 유효했음을 실증하였다 — Tier2/3의 실제 실행 확인(`executed`, 웹훅 응답 후 실행 기록까지 확인) 건수가 0건(파일럿)에서 다수 건(본실험)으로 증가하였다.

**요약 지표** (Tier2와 Tier3는 §4.9와 동일하게 동일 H_pre 생성 결과를 공유하며 채점 방식만 다르다):

| 지표 | Tier 1 (Raw LLM) | Tier 2 (H_pre, raw) | Tier 3 (H_pre+H_post, corrected) |
|---|---|---|---|
| PCR (평균) | 0.793 | 0.840 | 0.865 |
| PCR 완전정합률 | 24.0% | — | 39.7% |
| SA (평균) | 0.968 | 0.998 | 0.998 |
| WIS (평균, 낮을수록 우수) | 0.112 | — | 0.252 |
| EFR (비율) | 88.9% | 98.4% (raw) | 98.4% (corrected) |
| RCR (평균) | — | — | 15.1% |

**유효 표본 수가 지표별로 다른 이유**: 아래 각 검정의 n은 330에서 일부 감소하는데, 이는 표본 부족이 아니라 쌍대 비교의 전제조건(양쪽 Tier 모두에서 해당 지표가 계산 가능해야 함)에 따른 제외 때문이다 — PCR은 일부 문항에서 워크플로우 JSON 코드 블록을 추출하지 못해(n=312), EFR은 일부 문항에서 실행 검증 응답 자체를 얻지 못해(n=320) 쌍대 비교에서 제외되었다. 330문항은 §4.3이 산정한 최소 표본(조건당 91건)을 지표별 유효 n(312/329/320) 기준으로도 모두 충분히 상회한다.

**가설 검정 요약**:

| 가설 | 내용 | 결과 | 핵심 수치 |
|---|---|---|---|
| H1 | Tier3의 PCR이 Tier1보다 높다 | **지지** | GEE OR=1.556 [1.352,1.791], Wilcoxon p<0.0001, McNemar(완전정합 24.0%→39.7%) p<0.0001 |
| H2 | Tier3의 WIS가 Tier1보다 낮다(적다) | **지지되지 않음 — 반대 방향 유의** | LMM β=+0.139, p=0.017; Wilcoxon p=0.021(보정 후 0.042) |
| H3 | Tier3(corrected)의 EFR이 Tier2(raw)보다 높다 | **지지되지 않음** | GEE 계수≈0, p=0.9999; McNemar p=1.0 |
| H4 | 개선 효과가 GPT-4o·Gemini에 공통 | **미평가** | Gemini API 키 미보유로 이번 실행에서 제외 |
| H5 | RCR과 파라미터명 길이가 음의 상관 | **지지** | Spearman ρ=-0.584(n=221), p<0.0001 |

**가설별 상세 해석 — 1차 분석(질의 내 군집성을 고려한 회귀모형: PCR·EFR은 이항 GEE, WIS는 질의 무작위 절편 선형혼합모형)과 강건성 검정(McNemar·Wilcoxon)의 이중 확증**:

- **H1(PCR) — 지지됨.** 1차 분석: 파라미터 단위 이항 GEE(질의 군집화, n=4,950 파라미터)에서 Tier 계수 log-odds=0.442(p<0.0001), 승산비(OR)=1.556(95% CI [1.352, 1.791]) — Tier3의 파라미터가 유효할 오즈가 Tier1 대비 약 1.56배 높다. 강건성 검정: Wilcoxon 부호순위검정(n=312) 평균 차이 +0.073(95% CI [0.052, 0.094]), p<0.0001; 완전정합 이분화 McNemar 검정(24.0%→39.7%, Cohen's h=0.339) 역시 p<0.0001. 세 방법(GEE·Wilcoxon·McNemar)이 완전히 일치하며, N=30 파일럿에서 "유의수준에 근접"했던 신호가 본실험에서 확고한 확증으로 이어졌다.
- **H2(WIS) — 지지되지 않았으며, 예측과 반대 방향으로 유의함.** 1차 분석: 질의 무작위 절편 선형혼합모형에서 Tier 계수=0.139(p=0.017, 95% CI [0.025, 0.253]). 강건성 검정: Wilcoxon(n=329) p=0.021(Holm-Bonferroni 보정 후 0.042, 여전히 유의). 즉 Tier3의 WIS가 Tier1보다 유의하게 **높다**(나쁘다) — H2가 예측한 방향과 정반대다. §4.9에서 N=30 문항 단위로 추적한 원인 분석(규칙 기반 검증기가 실제 존재하는 구조적 결함 — responseMode/Respond to Webhook 조합, Merge 노드 입력 수 — 을 정확히 탐지한 참 양성이었다는 사례 분석)이 N=330에서도 동일한 방향으로 재현되었다. **다만 본 결과만으로 사후 처리 하네스가 구조적 오류를 증가시켰다고 해석하기는 어렵다.** 오류 사례를 추적한 결과, WIS 증가분은 대부분 규칙 기반 검증기가 산출물에 기존부터 존재하던 구조적 위반을 추가로 탐지하면서 발생하였다 — 즉 Tier1(raw)에도 유사한 결함이 있었을 가능성을 배제할 수 없으나, Tier1의 산출물에는 동일한 검증기가 적용되지 않는 관계로 이 비교는 "Tier1은 원래 결함이 적다"가 아니라 "규칙 기반 검증기가 Tier3의 특정 생성 패턴에서만 결함을 확인할 수 있다"는 **Tier 간 검증 민감도의 비대칭**을 반영한다. 그 근본 원인은 규칙 기반 검증기의 점검 범위가 병합 노드·웹훅·Code 노드 세 가지로 좁고(§5.3), 그 점검 대상이 정확히 H_pre가 유도하는 생성 패턴과 겹치기 때문으로 해석하는 것이 데이터와 일치한다. 이는 §5.3의 검증기 커버리지 확장 과제가 왜 중요한지를 N=330 규모에서 통계적으로 뒷받침하는 근거다.
- **H3(EFR) — 지지되지 않음(귀무가설 기각 실패).** 1차 분석: 질의 단위 이항 GEE에서 Tier 계수≈0.000(p=0.9999). 강건성 검정: McNemar p=1.0, Cohen's h=0.0. Tier2(raw)와 Tier3(corrected) 모두 98.4%로 완전히 동일하다. 유의할 점은, H3가 묻는 것은 Tier2(H_pre만 적용)에서 Tier3(H_post까지 적용)로 갈 때의 **추가** 개선 여부이며, Tier1(Raw)에서 Tier2로 갈 때는 EFR이 88.9%→98.4%로 이미 9.5%p 크게 개선되어 있었다는 점이다. 즉 실행 가능성 개선의 대부분은 H_pre 단계에서 이미 일어났고, 그 이후 H_post가 추가로 개선할 여지가 거의 남지 않은 천장 효과가 관측된 것이다. RCR이 15.1%로 낮아(GPT-4o가 이미 파라미터명을 비교적 정확히 생성해 교정이 발생하는 사례 자체가 상대적으로 드묾) 교정 개입 자체가 드물었다는 §4.9의 해석과도 정합적이며, 이는 "H_pre가 실행 가능성 개선의 주 동인이고 H_post는 보완적 역할을 한다"는 본 연구 설계 의도(§3.1)와 부합하는 결과로 해석한다.
- **H5(RCR과 파라미터명 길이) — 지지됨, 표본 규모에 걸쳐 안정적으로 재현.** Spearman ρ=-0.584(n=221, p<0.0001)로 강한 음의 상관관계가 관찰되었다. N=90 중간 점검 시 -0.687, N=210 시 -0.659, N=330 최종 -0.584로 표본이 늘수록 다소 완화되었으나 뚜렷한 음의 연관은 일관되게 유지되었다. 이 결과는 상관관계이며 인과관계를 주장하지 않는다 — 다만 편집 거리 임계값 ≤2가 고정되어 있다는 점을 함께 고려하면, 파라미터명이 길수록 같은 임계값 내에서 교정에 성공할 확률이 낮아지는 경향과 부합하며, §5.3의 "파라미터 길이 기반 적응적 임계값" 향후 과제에 직접적인 정량적 근거를 제공한다.

**종합**: 본실험은 PCR(H1)과 RCR-길이 상관(H5)에서는 프레임워크의 효과를 명확히 지지하였으나, WIS(H2)에서는 예측과 반대 방향의 유의한 결과를 얻었고 EFR(H3)에서는 유의한 차이를 확인하지 못하였다. 이는 논문의 핵심 주장을 무너뜨리는 결과가 아니라, 처음 제시했던 "전주기 하네스가 전반적으로 유익할 것"이라는 다소 일반적인 기대를 "H_pre가 파라미터 정합성·실행 가능성 개선의 실질적 동인이며, H_post의 교정 효과는 이번 벤치마크에서는 제한적이었고, 규칙 기반 검증기는 실제 결함을 탐지하는 동시에 좁은 커버리지로 인한 측정 편향도 함께 드러낸다"는 훨씬 구체적인 진술로 정제해 주는 결과다. 평가 지표별로 나타난 이 이질적 결과 자체가 §4.2에서 강조한 "결정론적 자동 채점"의 가치 — 지표의 정의와 한계가 명시적이어서 이런 세분화된 해석이 가능하다는 점 — 를 실증적으로 뒷받침한다. 교차모델 일반화(H4)·환각률(HR)·재현성(DRR)은 이번 실행에서 검증하지 않았으므로, 위 결과가 모델 독립적이라거나 환각을 직접 감소시켰다는 주장으로 일반화하지 않는다.

## 5. 결론 및 향후 연구

### 5.1 결론

본 연구는 온톨로지 기반 문맥 그라운딩과 규칙 기반 판단을 결합한 통제형 LLM 프레임워크를, 출력 공간이 개방적이고 구조적으로 복잡한 노코드 자동화 도메인에 맞추어 H = (H_pre, H_post, H_exec)의 3단계 하네스 구조로 정식화하였다(§2.6, §3.1). 온톨로지를 723개 노드·787개 관계·30개 제약 규칙으로 구성된 5계층 구조로 설계하고 자동화된 스크립트로 내적 일관성(모순 0건)을 검증하였으며, 순수 규칙 기반 의도 분류의 실패 경험을 바탕으로 규칙·LLM·키워드를 결합한 하이브리드 라우팅으로 전환하였다. 무엇보다 생성 이후 단계를 "능동적 교정"과 "진단적 검증"으로 명확히 분리함으로써 예방적 환각 억제만으로는 부족한 개방형 코드 생성 도메인에 적합한 책임 분리 구조를 제시하였다. 아울러 본 연구는 평가 방법론 자체를 연구 기여의 일부로 삼아, 결정론적 자동 채점과 주관적 인간 판정을 명확히 분리하고, 검정력 분석에 기반한 표본 설계와 질의 내 군집성을 고려한 회귀모형(GEE·선형혼합모형)·McNemar·Wilcoxon을 병행하는 통계 분석 계획을 사전에 확정한 뒤, WORKFLOW_BUILD 인텐트 N=330 규모로 이를 실제로 실행하였다(§4.10).

최종 결과가 말해주는 것은 하나의 단일한 결론이 아니라, 가설별로 갈리는 구체적인 그림이다. 파라미터 정합률(PCR)에서는 1차 분석(GEE)과 강건성 검정(Wilcoxon·McNemar)이 모두 p<0.0001로 일치하는 명확한 개선을 확인하였고(파라미터 단위 승산비 1.56, 완전정합률 24.0%→39.7%), 규칙 기반 교정기의 편집 거리 임계값 설계를 뒷받침하는 강한 음의 상관(RCR-파라미터명 길이, ρ≈-0.58~-0.69)도 표본 규모에 걸쳐 안정적으로 재현되었다 — 이 둘은 확증되었다. 반면 사후 처리 하네스가 실행 가능률(EFR)을 추가로 개선하는지를 묻는 가설(H3)은 지지되지 않았다(Tier2 98.4%→Tier3 98.4%, p=1.0) — 다만 이는 사후 교정이 무의미하다는 뜻이 아니라, Raw 대비 H_pre 단계에서 이미 EFR이 88.9%→98.4%로 크게 개선되어 H_post가 추가로 개선할 여지 자체가 작았다는 뜻이며, 이는 H_pre(사전 생성 통제)가 실행 가능성 개선의 주된 동인이고 H_post(사후 교정)는 보완적 역할에 머문다는 본 연구의 설계 의도와 부합한다. 가중 이슈 점수(WIS)는 예측과 반대 방향으로 유의한 결과를 보였는데(Tier1 0.112→Tier3 0.252), 오류 사례를 추적한 결과 그 증가분은 규칙 기반 검증기가 기존에 존재하던 구조적 위반을 추가로 탐지하면서 발생한 것으로 확인되어, 이 결과만으로 사후 처리 하네스가 구조적 오류를 늘렸다고 해석하기보다 규칙 기반 검증기의 제한된 점검 범위와 Tier 간 검증 민감도의 비대칭이라는 측정상의 한계로 해석하는 것이 데이터와 부합한다(§5.3). 교차모델 일반화(H4)·환각률(HR)·재현성(DRR)은 이번 실행 범위에서 검증하지 않았으므로, 위 결과를 모델 독립적이거나 환각을 직접 감소시켰다는 주장으로 확장하지 않는다. 이러한 지표별 이질적 결과는 §4.2에서 강조한 결정론적 자동 채점의 가치 — 지표의 정의와 한계가 명시적이어서 이런 세분화된 해석이 가능하다는 점 — 를 실증적으로 뒷받침한다.

### 5.2 구현 현황에 대한 정직한 보고

본 연구는 이전 버전에서 설계되었으나 시스템에 실제로 연결되지 않았다고 보고했던 두 구성요소를 이번 버전에서 실제로 연결·배포·라이브 검증하였다. 첫째, 레이어 5(LearningGraph, 17개 학습 개념의 선행 의존성 그래프)는 이제 `CurriculumService`(`server/workflow_services.py`)에서 실제로 조회된다. 유저 요청에서 온톨로지가 노드를 감지하면(`OntologyEnhancer.enhance()`), 그 노드들과 `node_types`가 가장 많이 겹치는 LearningGraph concept을 찾고, `get_learning_prerequisites()`로 해당 concept까지의 선행 학습 체인을 위상 정렬 순서로 추적하여 주차 수·난이도·주차별 대상 노드를 결정론적으로 확정한 뒤 LLM에게 "이 구조를 그대로 따르라"고 지시한다 — 정규식 기반 레벨 감지는 특정 주제가 감지되지 않는 일반적인 요청에 대한 폴백으로만 남겨두었다. 둘째, 감지된 노드를 기준으로 검색 결과 순위를 재조정하는 온톨로지 재랭킹 함수(`OntologyEnhancer.rerank_chunks()`)도 이제 일반 Q&A 경로(`server/general_rag.py`)와 워크플로우 생성·커리큘럼·표현식 생성 경로가 공유하는 검색 헬퍼(`_rag_with_filter()`)에 실제로 연결되어, 검색 결과 중 감지된 노드 및 그 관계(RelationGraph)에 등장하는 노드명을 언급하는 청크에 가산점을 부여해 재정렬한다. 두 연결 모두 배포 후 라이브로 검증하였다 — LearningGraph 연결은 "웹훅 받아서 슬랙으로 알림 보내는 자동화 커리큘럼 짜줘"라는 실제 요청에 대해 `ontology_matched_concept: "triggers"`, 2주차 구성(1주차 n8n_basics, 2주차 triggers)이 그래프 구조와 정확히 일치하는 결과를 확인하였고, 재랭킹 연결은 하위 순위(6위)의 관련 청크가 재정렬 후 3위로 상승하는 것을 직접 확인하였다. 셋째, H_exec(런타임 실행 하네스)는 n8n Public REST API에 워크플로우를 생성(스키마 검증 통과)하는 부분에 더해, 웹훅 트리거 워크플로우에 한해 실제 발행·트리거·실행결과 확인까지 구현·배포되어 라이브 검증을 마쳤다(`server/workflow.py`의 `_verify_execution`, §3.7). 다만 이는 n8n Public API 자체가 API 키만으로 임의 트리거 타입을 즉시 실행하는 기능을 제공하지 않는다는 플랫폼 제약에 따른 것으로, 수동/스케줄/앱별 트리거 워크플로우에 대해서는 여전히 스키마 검증까지만 자동 판정한다 — §4.7의 평가 실험에서 EFR을 자동 채점할 때 이 범위 제한을 반영해야 한다. 이 세 항목의 연결은 결함 수정이 아니라, 이미 구현되어 있던 데이터 구조·함수를 실제 서비스 흐름에 배선한 것이다. 넷째, §4에서 설계한 평가 방법론 중 WORKFLOW_BUILD 인텐트에 대한 N=330 본실험(§4.10)은 실제로 실행을 완료하였다 — 질의 내 군집성을 고려한 회귀모형(PCR·EFR은 GEE, WIS는 선형혼합모형) 1차 분석과 McNemar/Wilcoxon 강건성 검정이 일치하는 결과로 H1(PCR)과 H5(RCR-길이 상관)를 지지하고, H2(WIS)에서는 예측과 반대 방향의 유의한 결과를, H3(EFR)에서는 유의한 차이 없음을 확인하였다. 다만 이는 §4.3이 원래 설계한 3개 인텐트(워크플로우 설계/표현식 생성/에러 진단) 균등 배분이 아니라 WORKFLOW_BUILD 단일 인텐트에 전량을 배정한 결과이며, 벤치마크 질의도 §4.3이 요구한 "약 40% 실제 커뮤니티 수집" 없이 전량 체계적 자동 생성으로 구성되었다(§4.10, §4.8 외적 타당성 한계). Gemini 교차모델 검증(H4)·HR(인간 판정)·DRR(재현성)은 각각 API 키 미보유·별도 웹 도구 구축·비용 문제로 이번 실행 범위에서 의도적으로 제외하였다. §3.2의 "예비 실행 점검"과 §4.9의 N=30 파일럿은 이 N=330 본실험이 실제로 안정적으로 작동함을 사전에 검증한 단계적 절차였다.

### 5.3 향후 연구

본 연구는 다음과 같은 한계와 향후 연구 방향을 가진다. 첫째, LearningGraph의 CurriculumService 연결은 완료되었으나(§5.2), 연결 이전의 순수 정규식 기반 레벨 감지 방식과 연결 이후의 선행 의존성 그래프 기반 방식이 실제 생성되는 커리큘럼의 품질(주차 구성의 논리적 정합성, 학습자 만족도 등)에 어떤 차이를 만드는지에 대한 정량적 비교 연구는 아직 수행되지 않았다. 둘째, 온톨로지 재랭킹 함수의 검색 파이프라인 연결도 완료되었으나(§5.2), 재랭킹 적용 전/후로 검색 정확도가 실제로 개선되는지를 정보검색 지표(nDCG, MRR 등)로 정량 검증하는 연구는 아직 수행되지 않았다. 셋째, 규칙 기반 교정기의 교정 임계값(편집 거리 ≤2)은 현재 경험적으로 설정된 값이다 — §4.10의 N=330 본실험에서 RCR(교정 성공률)과 파라미터명 길이 간 Spearman 상관이 ρ=-0.584(p<0.0001, N=90·N=210 중간 점검에서도 각각 -0.687·-0.659로 일관되게 강한 음의 상관)로 확증되어, 파라미터 길이 기반 적응적 임계값으로 개선할 정량적 근거가 마련되었다. 이를 실제로 구현하고 고정 임계값 대비 PCR·RCR 개선 효과를 검증하는 것이 다음 과제다. 넷째, 현재 규칙 기반 검증기는 위반을 진단만 하고 자동 교정하지 않는데, REQUIRES/CONDITIONAL처럼 교정 방향이 명확한 제약 위반(예: `retryOnFail: true` 설정 시 `maxTries` 자동 추가)에 한해 제한적으로 자동 교정을 확장하는 것이 가능한지 검토할 필요가 있다. 다섯째, 규칙 기반 검증기의 관계·패턴 진단(Stage 3)이 현재는 병합 노드·웹훅·Code 노드에 대한 세 가지 하드코딩된 검사에 한정되어 있어, 레이어 2(RelationGraph)의 787개 관계 전체를 실제로 조회하는 일반화된 검증 로직으로 확장하는 연구가 필요하다 — §4.9의 N=30 파일럿에서 WIS가 예상과 반대 방향(Tier3가 Tier1보다 높음)으로 관측된 원인을 추적한 결과, 30문항 중 단 2건만 이 세 가지 검사에 걸렸다는 좁은 커버리지가 직접적 원인으로 확인되었다. §4.10의 N=330 본실험에서도 동일한 방향의 유의한 차이(GLMM p=0.017, Wilcoxon p=0.021)가 재현되어, 좁은 검증기 커버리지가 WIS 해석에 미치는 영향이 표본 규모와 무관하게 실증적으로 뒷받침되었다 — 이 확장은 더 이상 이론적 가능성이 아니라 관측된 측정 편향을 해소하기 위한 우선순위 높은 과제다. 여섯째, 본 연구의 교차모델 검증은 GPT-4o·Gemini 두 모델에 한정되므로, 오픈소스 모델(Llama, Qwen 등)로 확장했을 때도 개선 효과가 재현되는지 검증하는 후속 연구가 필요하다. 일곱째, 구성 타당성의 한계로 다루지 못한 사용자 유용성·만족도를 실제 n8n 사용자 대상 통제된 사용성 평가(예: 과제 완료 시간, 주관적 만족도 리커트 척도)로 보완할 필요가 있다. 여덟째, 향후 시장에 지배적인 n8n 전문 AI 제품이 등장할 경우, §2.4에서 논의한 재현성·엔진 통제 문제를 완화할 수 있는 실험 설계를 마련해 3자 비교로 확장하는 것도 가능하다. 아홉째, §3.2의 사전 맥락 확장이 노드 누락을 실제로 얼마나 완화하는지는 아직 정량적으로 검증되지 않았다 — 사전 맥락 확장 적용 전/후로 목적 서술형 벤치마크 하위셋에 대한 노드 누락률(Node Omission Rate: 정답 워크플로우에 존재하나 생성 결과에서 빠진 필수 노드의 비율)을 측정하는 추가 ablation을 §4의 실험 설계에 포함시키는 것이 향후 과제다. 열째, §4.7의 평가 실험에서 H_exec가 탐지하는 잔존 실행 실패를 유형별로 분석한 뒤, 그중 H_pre 단계의 온톨로지·RAG 재검색으로 해소 가능한 유형이 확인된다면, H_exec의 실패 신호를 H_pre로 되먹여 제한된 범위 내에서만 재생성을 시도하는 경계 지정형 복구 루프(Bounded Repair Loop)를 실험적으로 도입하는 것을 검토할 수 있다. 이는 현재의 파이프라인 구조를 선제적으로 확장하는 것이 아니라, 잔존 실패의 원인 분포를 먼저 실증적으로 확인한 뒤 그 결과가 뒷받침하는 경우에 한해 추가하는 것을 원칙으로 한다. 열한째, §3.7의 실행 검증 기능을 실제 배포 환경에서 라이브로 검증하는 과정에서, 스키마 검증은 통과하지만 실제 실행에서만 드러나는 구체적인 결함 유형을 실증적으로 확인하였다 — LLM이 `n8n-nodes-base.code`(신규 Code 노드) 타입에 구버전 Function 노드의 파라미터 키 `functionCode`를 사용하여(신규 노드가 요구하는 키는 `jsCode`) 실행 시점에만 실패하는 사례이다. 현재 규칙 기반 교정기는 편집 거리 ≤2 이내의 오탈자만 교정하도록 설계되어 있어("functionCode"와 "jsCode"는 편집 거리가 이 범위를 크게 벗어난다), 이러한 신구 파라미터명 치환(alias) 유형의 오류는 구조적으로 교정 대상에서 제외된다. 이는 오탈자 교정과는 성격이 다른 별도의 교정 규칙(알려진 구버전-신버전 파라미터명 매핑 테이블)이 필요함을 시사하며, §4.7의 실제 벤치마크에서 이러한 유형의 실패가 유의미한 빈도로 관찰되는지 먼저 확인한 뒤 도입 여부를 결정하는 것이 바람직하다.

| **v22 (본 버전)** | **N=330 결과에 대한 정밀 검토 피드백을 반영해 통계 표기·해석의 정확도를 높임(수치 자체는 변경 없음).** (1) **통계 방법 명칭 정정**: PCR·EFR은 GEE(일반화추정방정식), WIS는 선형혼합모형(LMM)으로 서로 다른 모형인데 v21에서 "GLMM/GEE"로 뭉뚱그려 표기한 것을 "질의 내 군집성을 고려한 회귀모형(PCR·EFR: GEE / WIS: 선형혼합모형)"으로 §4.10·§5.1·§5.2와 `eval/analyze_pilot.py`(리포트 생성기) 전체에서 일관되게 정정.
