## 1. OpenAI Harness Engineering이란 무엇인가

### 1.1 등장 배경

OpenAI의 Codex 팀이 2026년 초, 다음과 같은 실험을 근거로 이 용어를 제시했습니다.

- 약 **100만 줄 규모의 실제 프로덕션 베타 제품**을 구축·출시
- **사람이 직접 작성한 코드 0줄** — 모든 코드가 Codex 에이전트에 의해 생성됨
- 팀 규모 3명, 약 5개월 소요
- 엔지니어의 역할이 "코드를 작성하는 것"에서 "에이전트가 신뢰성 있게 코드를 작성하도록 만드는 시스템(=harness)을 설계하는 것"으로 이동했다는 것이 핵심 주장

이 경험을 바탕으로 OpenAI는 "이제 개별 코드 작성이 아니라, 에이전트를 둘러싼 **하네스(harness)**를 설계하는 것이 엔지니어링의 핵심이 되는 시대(agent-first world)"라는 프레이밍을 제시했습니다. 비슷한 시기 Anthropic, Stripe 등 다른 엔지니어링 조직에서도 유사한 실천이 관찰되었다고 보고됩니다.

### 1.2 핵심 정의 — "Agent = Model + Harness"

OpenAI가 제시한 핵심 공식은 다음과 같습니다.

> **Agent = Model + Harness**

여기서 harness는 "모델과 과제(task) 사이에 위치하는 실행 시스템"으로, 다음을 포괄합니다.

- 문맥 수집(context gathering)
- 도구 호출(tool invocation)
- 샌드박스/승인 경계 설정(sandbox and approval boundaries)
- 실행 진행상황 스트리밍(execution progress streaming)
- 멀티턴 세션에 걸친 작업 연속성 유지(carrying work across multi-turn sessions)

즉 harness는 "모델의 원시 추론 능력(raw reasoning)"을 "신뢰할 수 있는 실제 행동(dependable action)"으로 바꿔주는 **모델 주변의 모든 스캐폴딩(scaffolding)**을 가리키는 포괄적 용어입니다.

### 1.3 harness의 구성 — 3대 축과 3개 레이어

여러 소스에서 공통적으로 등장하는 분해는 두 가지입니다.

**(A) 3대 축(pillars)** — OpenAI가 명시했다고 보고되는 구조:

| 축 | 역할 |
|---|---|
| **Constraints (제약)** | 모델의 출력 공간을 규제 — 무엇을 하지 못하게 막을 것인가 |
| **Observability (관찰가능성)** | 모델의 추론·도구 호출 궤적(trajectory)을 모니터링 |
| **Feedback Loops (피드백 루프)** | 지속적인 능력 개선을 위한 신호 제공 |

**(B) 3개 레이어(layers)** — 실무적 구현 관점의 분해:

| 레이어 | 내용 |
|---|---|
| **Instruction layer** | 과제 목표, 프로젝트 컨벤션, 제약, 관련 문서 포인터 제공 |
| **Tool layer** | 파일 편집, 셸 명령, 테스트, 시뮬레이터, 로깅, 배포 스크립트 등 실행 가능한 액션 노출 |
| **Environment layer** | 의존성, 컨테이너, 런타임 버전 등 실행 환경 정의 |

Martin Fowler는 이를 조금 다르게 재구성하여 **context engineering(에이전트가 아는 것을 큐레이션) / architectural constraints(결정론적 린터·구조 테스트) / entropy management(문서 드리프트를 주기적으로 복구하는 보조 에이전트)** 세 축으로 설명하며, 특히 "harness는 코드가 어떻게 작성·조직되는지는 강제할 수 있지만, 그 코드가 실제 사용자가 원하는 것을 하는지는 아직 검증하지 못한다"는 한계를 지적합니다 — 구조적 정합성(mechanical하게 강제 가능)과 기능적 정확성(사람·제품과의 깊은 피드백 루프 필요)은 서로 다른 문제라는 것입니다.

### 1.4 검증 메커니즘

harness는 린터, 타입 체커, 유닛 테스트 같은 "변경되지 않는(rigid) 결정론적 소프트웨어 테스트"를 이용해, 에이전트의 출력이 검증을 통과하기 전까지는 **물리적으로 작업 완료를 막는** 방식으로 동작한다고 설명됩니다. 즉 harness는 단순 가이드라인이 아니라 **강제(enforcement) 메커니즘**입니다.

## 2. 본 연구의 H = (H_pre, H_post, H_exec)와의 관계

### 2.1 구조적으로 놀랍도록 유사한 3분할

가장 먼저 짚어야 할 사실은, 본 연구가 (OpenAI 문서를 참고하지 않고) 독자적으로 설계한 H_pre/H_post/H_exec 3단 구조가 OpenAI의 "Constraints / Observability / Feedback Loops" 3대 축과 **역할 수준에서 상당히 대응**된다는 점입니다.

| 본 연구 | OpenAI 3대 축(대응 관계) | 대응 근거 |
|---|---|---|
| **H_pre** (사전 생성 하네스) | **Constraints** | 생성 시작 전에 입력 문맥과 출력 형식을 제약 — 출력 공간을 미리 규제한다는 점에서 동일한 역할 |
| **H_post** (사후 처리 하네스) | **Feedback Loops**에 가장 근접 (교정이라는 점에서는 일부 Constraints 성격도 있음) | 생성 결과를 사후에 검사·교정 — 결과에 대한 피드백을 즉시 적용한다는 점에서 대응 |
| **H_exec** (런타임 실행 하네스) | **Observability**+검증(verification) | 실행 가능 여부를 외부 환경에서 관찰·판정 |

이것은 우연이 아니라, "모델을 신뢰할 수 없는 블랙박스로 취급하고 그 앞·뒤·바깥을 감싼다"는 동일한 공학적 직관에서 독립적으로 수렴한 결과로 해석할 수 있습니다. **이 수렴 자체가 논문에서 방어 논리로 쓸 수 있는 유용한 근거**입니다 — "우리가 임의로 3단계를 나눈 것이 아니라, 업계 최전선(OpenAI)에서도 독립적으로 유사한 3분할에 도달했다"는 정황적 타당성(convergent validity) 논증이 가능합니다.

### 2.2 근본적인 스코프 차이 — 여기가 핵심 유의점

동시에, 두 개념은 **적용 대상 시스템의 종류 자체가 다릅니다.**

| 구분 | OpenAI Harness Engineering | 본 연구의 H=(H_pre,H_post,H_exec) |
|---|---|---|
| 대상 시스템 | **자율(autonomous) 멀티턴 에이전트** (Codex가 수개월간 스스로 코드베이스를 발전시킴) | **단일 턴(single-turn) 응답 생성** (질의 1건 → 응답 1건) |
| 시간 지평 | 장기간(수 주~수개월)에 걸친 연속 작업 | 하나의 요청-응답 사이클 |
| 도구 호출(tool-calling) | 핵심 요소 (파일 편집, 셸 명령, 배포 등 임의 액션 실행) | 없음 — 워크플로우 JSON을 생성하고 검증할 뿐, 에이전트가 스스로 도구를 호출하며 반복 작업하지 않음 |
| 샌드박스/승인 경계 | 핵심 요소 (에이전트가 위험한 행동을 하지 못하도록 하는 실행 격리) | 해당 없음 |
| 멀티턴 세션 연속성 | 핵심 요소 | 해당 없음 (매 질의가 사실상 독립적으로 처리됨) |
| 적용 도메인 | 범용 (소프트웨어 개발 전반) | 특정(n8n 워크플로우 자동화)의 개방형 출력 도메인 환각 통제 |
| 목적 | 신뢰할 수 있는 자율 행동 확보 | 환각 억제 + 실행 가능성 검증 |

즉, OpenAI의 harness는 **"에이전트가 스스로 여러 단계에 걸쳐 행동하게 만드는 범용 스캐폴딩"**이고, 본 연구의 H는 **"단일 응답 생성 파이프라인을 감싸는, 환각 통제에 특화된 3단계 검증·교정 장치"**입니다. 본 연구의 시스템은 OpenAI가 말하는 의미의 "에이전트"(자율적으로 도구를 호출하며 멀티턴에 걸쳐 작업하는 존재)가 아닙니다.

### 2.3 이것이 왜 REG 명칭 충돌보다 더 신중해야 하는 사안인가 (그러나 방향은 반대)

이전에 선배 논문과의 REG 약어 충돌을 처리했던 논리를 이번에도 적용해야 하지만, 성격은 정반대입니다.

- REG 사례: 같은 실험실 내 사전 공유되지 않는 소규모 선행 연구와 **우연히 같은 약어**가 겹친 것 → **혼동을 피하기 위해 우리 쪽 용어를 바꿈**(REG → "규칙 기반 교정기")
- 이번 사례: **업계에서 이미 표준화되고 있는(2026년 시점) 유명 용어**를 의도적으로 가져다 쓰려는 것 → 용어 자체는 바꿀 필요가 없지만(오히려 인지도가 논문에 유리), **스코프를 명시적으로 좁혀서 선언**하지 않으면 "우리 시스템이 OpenAI가 말하는 수준의 자율 에이전트 하네스를 구현했다"는 과장된 인상을 줄 위험이 REG 때보다 훨씬 큽니다. OpenAI는 압도적으로 유명한 1차 출처이기 때문에, 심사자가 "Harness Engineering"이라는 단어를 보면 자동으로 OpenAI의 정의(tool-calling, sandboxing, multi-turn autonomy)를 먼저 떠올릴 가능성이 높습니다.

따라서 이번에는 **용어를 재사용하되 범위를 반드시 좁혀서 못박는 문장**이 필요합니다.

## 3. 통합 권고안

### 3.1 결론부터: 통합을 권장합니다

득실을 비교하면 명확히 이득이 큽니다.

- **득**: (1) "Harness Engineering"이 저자가 지어낸 조어가 아니라 2026년 업계에서 실제로 통용되는 시의성 있는 용어임을 입증 → 논문의 최신성·타당성 강화. (2) OpenAI의 3대 축과 독립적으로 수렴했다는 사실을 convergent validity 논증으로 활용 가능. (3) 심사자가 "이 용어를 어디서 가져왔나"라는 의문을 갖기 전에 선제적으로 출처와 관계를 명시함으로써 오히려 인용 성실성 측면에서 플러스.
- **실(관리 가능)**: 스코프 혼동 위험 → 아래 3.2의 명시적 disambiguation 문장으로 해소 가능.

### 3.2 반영 위치별 제안 문구 (초안 — 확인 후 적용)

#### (1) §2에 신설 소절 "2.6 OpenAI Harness Engineering과의 관계" 추가 제안

§2.5(신규성에 대한 입장) 바로 뒤, §3 시작 전에 배치하는 것을 권장합니다. 논문에 "우리가 왜 이 용어를 쓰는지"와 "어디까지가 같고 어디부터 다른지"를 §3 본문 진입 전에 한 번에 정리해주는 위치입니다.

> **제안 문구 (초안)**
>
> 2026년 초 OpenAI는 Codex를 이용해 약 100만 줄 규모의 프로덕션 코드베이스를 사람이 직접 작성한 코드 없이 구축한 사례를 근거로 "Agent = Model + Harness"라는 프레이밍을 제시하며, 모델 자체가 아니라 모델을 둘러싼 문맥 수집·도구 호출·제약·검증 체계인 "harness"의 설계가 신뢰할 수 있는 에이전트 행동의 핵심이라고 주장하였다[15]. 본 연구가 §3.1에서 정의하는 H = (H_pre, H_post, H_exec)는 이러한 하네스 엔지니어링의 철학 — 모델 가중치를 수정하지 않고 모델을 둘러싼 시스템 계층으로 신뢰성을 확보한다는 관점 — 을 공유하지만, 그 적용 대상은 본질적으로 다르다. OpenAI가 다루는 하네스는 도구 호출·샌드박스 실행 경계·멀티턴 세션 연속성을 갖춘 자율 에이전트를 위한 범용 스캐폴딩인 반면, 본 연구의 H는 단일 턴 질의-응답 파이프라인에서 개방형 출력 도메인의 환각을 통제하기 위한 특화된 3단계 장치이다. 본 연구의 시스템은 스스로 도구를 호출하며 여러 단계에 걸쳐 작업을 수행하는 자율 에이전트가 아니므로, 이하에서 사용하는 "하네스 엔지니어링"은 OpenAI가 제시한 범용 에이전트 스캐폴딩 개념을 개방형 출력 도메인의 단일 턴 생성-검증 문제에 특화하여 재정식화한 좁은 의미로 한정한다.

#### (2) §3.1 정의 블록 직후 한 문장 보강

기존 문장(99행) "**정의(하네스 엔지니어링)**: 본 연구는 하네스 엔지니어링을 H = (H_pre, H_post, H_exec) 세 함수의 조합으로 정의한다." 바로 뒤에 아래 한 문장만 추가하는 최소 변경안입니다. §2.6을 신설하지 않고 최소한으로만 반영하고 싶을 경우 이 문장 하나만으로도 disambiguation 목적은 달성됩니다.

> **제안 문구 (최소 반영안)**
>
> 이 정의는 OpenAI[15]가 제시한 "Agent = Model + Harness" 프레이밍의 철학을 계승하되, 자율 멀티턴 에이전트가 아닌 본 연구의 단일 턴 개방형 출력 도메인 생성 문제에 맞추어 재정식화한 것으로, 도구 호출·샌드박스 실행 경계·세션 연속성과 같은 자율 에이전트 고유의 구성요소는 범위에 포함하지 않는다.

#### (3) 참고문헌 [15] 추가

> [15] OpenAI, "Harness Engineering: Leveraging Codex in an Agent-First World," OpenAI Blog, 2026. URL: https://openai.com/index/harness-engineering/ [Accessed: 2026-09-17].

기업 블로그를 학술 논문에 인용하는 것에 대한 정당성은, 이미 §1.1에서 확인한 대로 arXiv에 게재된 복수의 2026년 후속 연구들(`Natural-Language Agent Harnesses`, `AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents` 등)이 동일한 OpenAI 원문을 1차 출처로 인용하고 있다는 점에서 확보됩니다 — 즉 "기업 블로그이지만 이미 학계에서 인용 관행이 성립된 출처"입니다.

#### (4) §5.2(구현 현황 정직 보고)에 선택적으로 한 줄 추가 검토

이번 통합으로 "harness"라는 단어의 함의가 넓어지는 만큼, §5.2의 정직 보고 목록에 "본 연구의 시스템은 OpenAI가 정의하는 의미의 도구 호출·샌드박스·멀티턴 세션 연속성을 갖춘 자율 에이전트가 아니며, 이는 설계 목표에서 애초에 제외되어 있다"는 문장을 한 줄 추가하는 것을 고려할 수 있습니다. 이는 결함 보고가 아니라 **스코프를 스스로 명확히 긋는 문장**이므로, §5.2의 기존 톤("결함이 아니라 향후 연구의 확장 지점으로 보고")과 자연스럽게 어울립니다. 다만 §2.6(또는 §3.1 보강 문장)에서 이미 명시했다면 중복이 되므로, **§2.6/§3.1 중 하나 + §5.2 중복 방지** 원칙으로 셋 중 최대 2곳에만 배치하는 것을 권장합니다.

#### (5) §1 서론에는 반영하지 않는 것을 권장

서론(42행)의 "본 연구는 ... 3단계 하네스 엔지니어링 체계로 ... 프레임워크를 **독자적으로 설계**한다"는 문장은 그대로 유지하는 것을 권장합니다. 서론 단계에서부터 OpenAI를 언급하면 "독자적 설계"라는 주장과 충돌하는 인상을 줄 수 있습니다. 관계 설명은 §2(배경)로 미루고, 서론은 지금처럼 문제의식과 기여 중심으로 유지하는 것이 논증 순서상 더 안전합니다.

## 4. 종합 의견

OpenAI의 Harness Engineering은 (a) 본 연구가 독립적으로 도달한 3단계 구조와 철학적·구조적으로 수렴한다는 점에서 논문의 설득력을 높여줄 좋은 재료이고, (b) 동시에 자율 에이전트라는 훨씬 넓은 스코프를 가진 용어이므로 **범위를 명시적으로 좁히는 한 두 문장 없이는 인용하지 않는 것을 권장**합니다. 위 3.3의 **B안(표준 반영)** — §2.6 신설 소절 + §3.1 한 문장 보강 + 참고문헌 [15] 추가 — 을 기본으로 권장드리며, 이 방향에 동의하시면 실제 논문 파일(`paper_draft_ontology_controlled_llm.md`)에 바로 반영하겠습니다.
