# Part B — 여행 취향 프로필 (v2.0)

> **언제 묻는가**: 온보딩 때 **한 번** (이후 설정에서 언제든 수정 가능하지만, 여행 갈 때마다 다시 묻지 않는다).
> **무엇을 만드는가**: 사람이 잘 바뀌지 않는 "기본적으로 어떤 여행자인가"에 대한 상세 프로필. Part A(성향 점수)가 "왜 그런 선택을 하는가"라면, Part B는 "구체적으로 무엇을 좋아/기피하는가"다.
> **문항 수**: 46문항, 7개 섹션. **채점되지 않고 값 그대로 저장**되어 하드 필터·콘텐츠 매칭에 직접 쓰인다.
> 다른 파트: [Part A — 성향 진단](01-questionnaire-a-personality.md) · [Part C — 이번 여행 정보](03-questionnaire-c-trip.md) · [전체 개요](00-overview.md)

---

## 0. 이 파트를 왜 이렇게 길게 만들었나

Part A(16개 유형)는 "이 사람은 대략 어떤 여행자인가"라는 큰 그림만 잡아준다. 실제 추천이 정확하려면 그보다 훨씬 구체적인 정보 — 알레르기, 매운맛 정도, 숙소 필수 편의시설, 이동수단 선호 같은 것 — 가 필요하다. 이런 정보는 유형을 늘려서(32개, 64개…) 해결할 문제가 아니라, **한 번 제대로 물어보고 계속 재사용하는 프로필**로 해결하는 게 맞다. 그래서 Part B는 의도적으로 문항이 많다.

**단, 전부 필수는 아니다.** 46문항 중 안전·핵심 필터에 관련된 **14개만 필수**로 지정했고, 나머지는 선택이다. UI 구현 시:

- 온보딩에서는 필수 문항만 먼저 받고 "가입 완료".
- 이후 홈 화면에 "프로필 완성도 63% — 조금만 더 채우면 추천이 더 정확해져요" 같은 배너로 선택 문항을 점진적으로 채우게 유도한다 (progressive profiling).
- 섹션 단위(B-1~B-7)로 나눠 각각 별도 화면/카드로 구성하고 언제든 건너뛰고 나중에 이어할 수 있게 한다.

## 2. 이 데이터가 알고리즘에서 쓰이는 방식 (예시)

- `allergies[]`, `dietary_restriction`, `mobility_assistance` → [restaurant-recommendation-design.md](../restaurant-recommendation-design.md) 6.2절 **하드 필터**(제외 조건)에 직접 사용.
- `food_category_preferences[]`, `spice_tolerance`, `raw_food_tolerance` → 6.3절 `menu_match(u,r)` 콘텐츠 매칭의 입력.
- `lodging_amenity_requirements[]`, `lodging_top_priority` → 숙소 추천 엔진(9장, 향후 구현)의 하드 필터·스코어링에 재사용.
- `default_meal_budget_tier`, `default_lodging_budget_tier` → 사용자가 [Part C](03-questionnaire-c-trip.md)에서 이번 여행 예산을 따로 입력하지 않았을 때의 기본값(fallback)으로 사용.
- `top_spending_priority` → 식당·숙소·액티비티 간 예산 배분 가중치의 기본값.

## 3. 구현 메모

- `user_preference_profile` 테이블 DDL은 [restaurant-recommendation-design.md](../restaurant-recommendation-design.md) 3.4절에 추가되어 있다.
- 선택 문항은 매 응답마다 `profile_completeness`(0~100)를 재계산해 저장한다 — 프로그레시브 프로파일링 배너에 쓰인다.
- B1-1(선호 카테고리)과 B1-3(기피 카테고리)에 같은 항목을 동시에 고르지 못하도록 프론트에서 상호 배타 처리한다.
